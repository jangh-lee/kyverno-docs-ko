## 커뮤니티 패치 지원

Kyverno는 약 3개월 동안 커뮤니티 패치를 지원한다. 패치는 치명적인 버그 수정과 치명적 또는 높음 심각도의 CVE 수정으로만 엄격히 제한된다.

패치는 전용 릴리스 브랜치(예: `release-1.19`)에서 관리한다. 모든 패치는 신규 기능을 개발하고 테스트하는 `main`에 먼저 제출한 뒤 릴리스 브랜치로 cherry-pick한다.

**패치 지원 일정:**

|                                    |                                     |
| ---------------------------------- | ----------------------------------- |
| **지원 릴리스:**                   | v1.20 (릴리스: 2026년 11월)         |
| **예상 지원 종료:**                | v1.21 릴리스 (예상: 2027년 2월)     |
| **지원하는 쿠버네티스 버전:**      | v1.34 - v1.37                       |

다른 쿠버네티스 버전도 동작할 수 있지만 테스트하지 않았으므로 완전한 호환성은 보장하지 않는다.

릴리스 노트는 GitHub의 [kyverno/kyverno releases](https://github.com/kyverno/kyverno/releases)에서 볼 수 있다.

:::note[엔터프라이즈 지원]
장기 호환성과 프로덕션 지원을 확보하고 Kyverno 투자의 효과를 극대화하려면 **[상용 Kyverno 배포판](https://kyverno.io/support/)** 사용을 고려한다. 프로젝트를 유지 관리하는 벤더와 협력하면 Kyverno의 미래를 지키는 데 기여하면서 추가 혜택과 기능을 받을 수 있다.
:::

## 릴리스 관리

이 절은 릴리스 일정과 릴리스 브랜치 유지 관리 지침을 설명한다. 사용 가능한 모든 릴리스는 [kyverno/kyverno releases](https://github.com/kyverno/kyverno/releases)에서 볼 수 있다.

### 버전 관리

Kyverno는 [유의적 버전](https://semver.org/)(MAJOR.MINOR.PATCH) 체계를 사용한다.

#### MAJOR 릴리스

MAJOR 릴리스에는 대규모 기능, 설계 및 아키텍처 변경이 들어가며 호환되지 않는 API 변경이 포함될 수 있다. MAJOR 릴리스는 빈도가 낮고 필요할 때, 예를 들어 1년에 한 번 만든다.

#### MINOR 릴리스

MINOR 릴리스에는 하위 호환성을 유지하며 도입하는 기능, 개선, 수정이 들어간다. Kyverno는 빠르게 성장하는 프로젝트이면서 쿠버네티스 컨트롤 플레인의 핵심 컴포넌트이다. 그래서 몇 달에 한 번씩 릴리스를 내어 속도와 안정성의 균형을 맞춘다. 심각도가 중간 또는 낮음인 취약점은 기존 패치 릴리스와 겹치지 않는 한 MINOR 릴리스에 포함된다.

- 대략 3개월마다

#### PATCH 릴리스

PATCH 릴리스는 하위 호환되는 버그 수정, 안정성과 호환성에 영향을 주지 않는 아주 작은 개선, 치명적 또는 높음 심각도의 보안 취약점 수정을 위한 릴리스이다. 보통은 치명적인 수정만 PATCH 릴리스에 선별해 담는다.

- 치명적인 수정이 필요할 때 또는 대략 매월

### 브랜치, 태그, 버전

Kyverno는 GitHub 태그로 버전을 관리한다. 새 릴리스와 릴리스 후보는 와일드카드 태그 `v<major>.<minor>.<patch>*`로 게시한다.

태그가 없는 푸시도 릴리스 브랜치와 `main` 브랜치 모두에서 이미지를 빌드한다. 릴리스 브랜치(접두사가 `release-`인 브랜치)에 푸시한 커밋은 빌드를 만든 git SHA와 같은 태그로 이미지를 빌드한다. 그 브랜치에 푸시한 커밋에서 빌드한 최신 이미지에는 브랜치 이름의 롤링 태그가 다시 적용된다. 예를 들어 `release-1.10` 브랜치의 최신 커밋이 `19621b7a703935d6217a404ab5054687a84a3eda`이면, 빌드된 이미지에는 `19621b7a703935d6217a404ab5054687a84a3eda`와 `release-1.10` 태그가 붙는다. `main` 브랜치의 커밋도 비슷한 버전 전략을 따르지만, 롤링 태그로는 `latest`를 쓴다.

### 이슈

치명적이지 않은 이슈와 기능은 기본적으로 항상 다음 MINOR 릴리스 마일스톤에 추가한다.

우회 방법이 없는 치명적인 이슈는 다음 PATCH 릴리스에 추가한다.

### 브랜치와 PR

릴리스 브랜치와 PR은 다음과 같이 관리한다.

- 모든 변경은 항상 `main`에 먼저 커밋한다.
- MAJOR 또는 MINOR 릴리스마다 브랜치를 만든다.
- 브랜치 이름에는 `release-1.5`처럼 버전이 들어간다.
- PATCH 릴리스는 릴리스 브랜치에서 만든다.
- PATCH 릴리스에 포함해야 하는 치명적인 수정은 PR을 항상 `main`에 먼저 병합한 뒤 릴리스 브랜치로 cherry-pick해야 한다. 릴리스 브랜치에 병합할 PR에는 마일스톤 레이블(예: `milestone-1.5`)과 `cherry-pick-required` 레이블을 반드시 추가한다. PR을 cherry-pick(또는 병합)하면 `cherry-pick-completed` 레이블을 추가한다.
- 대응하는 이슈가 없는 PR은 추적을 위해 해당 마일스톤에 추가한다.
- 변경이 복잡하거나 브랜치가 크게 갈라졌다면 `main`과 릴리스 브랜치에 각각 PR이 필요할 수 있다.
- PR 리뷰에서는 Assignee 선택으로 리뷰어를 나타낸다.

### 릴리스 계획

MINOR 릴리스에는 기능, 개선, 버그 수정이 섞여 들어간다.

주요 기능은 [Kyverno Design Proposal(KDP)](https://github.com/kyverno/KDP/) 절차를 따른다.

릴리스를 시작할 때는 릴리스 마일스톤에 배정된 이슈가 많을 수 있다. 릴리스의 우선순위는 매주 열리는 메인테이너 회의에서 논의한다. 릴리스가 진행되면서 일부 이슈는 다음 마일스톤으로 옮겨질 수 있다. 따라서 중요한 이슈라면 릴리스 주기 초반에 우선순위를 주장하는 것이 중요하다.

### 릴리스 지침

릴리스 지침은 [release.md](https://github.com/kyverno/kyverno/blob/main/docs/dev/releases/create-a-release.md)를 참고한다.

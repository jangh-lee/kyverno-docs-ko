Kyverno 명령줄 인터페이스(CLI)는 리소스를 클러스터에 추가하기 전에 정책 동작을 검증하고 테스트하도록 설계되었습니다.

CLI는 CI/CD 파이프라인에서 리소스 작성 과정을 보조해, 배포 전에 리소스가 표준을 따르는지 확인하는 데 쓸 수 있습니다. `kubectl` 플러그인으로도, 독립 실행형 CLI로도 사용할 수 있습니다.

CLI는 Kyverno와 같은 코드베이스로 만들지만, 여러 설치 방법으로 제공되는 전용 바이너리입니다. 대상 Kubernetes 클러스터에서 파드로 실행되는 Kyverno 컨테이너 이미지와는 다릅니다.

이 페이지는 주요 Kyverno CLI 명령을 다룹니다. 다른 명령은 [레퍼런스 문서](/docs/kyverno-cli/reference/kyverno)를 참고하세요.

:::note[kustomize와 함께 사용하기]
Kyverno CLI를 [kustomize](https://kustomize.io/)와 함께 쓸 때는 `kubectl`에 내장된 버전보다 "[독립 실행형](https://kubectl.docs.kubernetes.io/installation/kustomize/binaries/)" 버전을 권장합니다.
:::

## Homebrew로 설치

Kyverno CLI는 [Homebrew](https://brew.sh/)의 [formula](https://formulae.brew.sh/formula/kyverno#default)로도 설치할 수 있습니다.

```sh
brew install kyverno
```

## Krew로 설치

[Krew](https://github.com/kubernetes-sigs/krew)로 Kyverno CLI를 설치할 수 있습니다.

```sh
# kubectl krew 플러그인 관리자로 Kyverno CLI 설치
kubectl krew install kyverno

# Kyverno CLI 테스트
kubectl kyverno version
```

## AUR(archlinux)로 설치

선호하는 AUR 헬퍼(예: [yay](https://github.com/Jguer/yay))로 Kyverno CLI를 설치할 수 있습니다.

```sh
yay -S kyverno-git
```

## GitHub Actions에 설치

GitHub Marketplace의 [kyverno-cli-installer](https://github.com/marketplace/actions/kyverno-cli-installer)로 GitHub Actions에 Kyverno CLI를 설치할 수 있습니다. 자세한 내용은 [kyverno-cli-installer](https://github.com/marketplace/actions/kyverno-cli-installer)를 참고하세요.

## 바이너리 수동 설치

[릴리스 페이지](https://github.com/kyverno/kyverno/releases)에서 컴파일된 바이너리를 직접 내려받아 Kyverno CLI를 설치할 수도 있습니다. 아래는 Linux x86_64 시스템에 Kyverno CLI v1.12.0을 설치하는 예시입니다.

```sh
curl -LO https://github.com/kyverno/kyverno/releases/download/v1.12.0/kyverno-cli_v1.12.0_linux_x86_64.tar.gz
tar -xvf kyverno-cli_v1.12.0_linux_x86_64.tar.gz
sudo cp kyverno /usr/local/bin/
```

## 소스에서 CLI 빌드

Git 저장소에서 CLI 바이너리를 직접 빌드할 수도 있습니다(Go 필요).

```sh
git clone https://github.com/kyverno/kyverno
cd kyverno
make build-cli
sudo mv ./cmd/cli/kubectl-kyverno/kubectl-kyverno /usr/local/bin/
```

## Apply 명령

`apply` 명령은 지원되는 CEL 기반 Kyverno 정책과 Kubernetes 네이티브 어드미션 정책을 리소스 매니페스트에 대해 평가합니다. `--cluster`를 지정하면 클러스터의 리소스에 대해 평가합니다. 지원되는 정책 유형은 변경 결과를 보여 주고 정책 리포트도 생성할 수 있습니다.

로컬 리소스에 정책을 적용합니다.

```sh
kyverno apply /path/to/policy.yaml --resource /path/to/resources.yaml
```

현재 Kubernetes 컨텍스트의 클러스터 리소스에 대해 정책을 평가합니다.

```sh
kyverno apply /path/to/policy.yaml --cluster
```

CLI는 Kubernetes `ValidatingAdmissionPolicy`와 `MutatingAdmissionPolicy`, 그리고 `ValidatingPolicy` 같은 Kyverno CEL 정책을 지원합니다. 다음 예시는 이 정책 유형을 로컬과 클러스터에 적용하는 방법을 보여 줍니다.

### Kubernetes 네이티브 정책 적용

`kyverno apply` 명령으로 Kubernetes 네이티브 정책과 해당 바인딩을 리소스에 적용할 수 있습니다. 클러스터 없이 로컬에서 정책을 테스트하는 데 씁니다.

#### ValidatingAdmissionPolicy 적용

`apply` 명령으로 Kubernetes ValidatingAdmissionPolicy를 다음과 같이 리소스에 적용할 수 있습니다.

정책 매니페스트(check-deployment-replicas.yaml):

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: check-deployments-replicas
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ['apps']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['deployments']
  validations:
    - expression: 'object.spec.replicas <= 3'
      message: 'Replicas must be less than or equal 3'
```

리소스 매니페스트(deployment.yaml):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-pass
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx-pass
  template:
    metadata:
      labels:
        app: nginx-pass
    spec:
      containers:
        - name: nginx-server
          image: nginx
```

ValidatingAdmissionPolicy를 리소스에 적용합니다.

```sh
kyverno apply /path/to/check-deployment-replicas.yaml --resource /path/to/deployment.yaml
```

다음과 같은 출력이 생성됩니다.

```sh
Applying 1 policy rule(s) to 1 resource(s)...

pass: 1, fail: 0, warn: 0, error: 0, skip: 0
```

아래 예시는 `ValidatingAdmissionPolicyBinding`을 정책과 함께 클러스터의 모든 리소스에 적용합니다.

정책 매니페스트(check-deployment-replicas.yaml):

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: 'check-deployment-replicas'
spec:
  matchConstraints:
    resourceRules:
      - apiGroups:
          - apps
        apiVersions:
          - v1
        operations:
          - CREATE
          - UPDATE
        resources:
          - deployments
  validations:
    - expression: object.spec.replicas <= 5
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: 'check-deployment-replicas-binding'
spec:
  policyName: 'check-deployment-replicas'
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        environment: staging
```

위 정책은 디플로이먼트 레플리카 수가 5를 넘지 않는지 검증하며, `environment: staging` 레이블이 붙은 네임스페이스로 범위를 제한합니다.

`environment: staging` 레이블이 있는 네임스페이스를 만듭니다.

```bash
kubectl create ns staging
kubectl label ns staging environment=staging
```

디플로이먼트 두 개를 만듭니다. 하나는 `staging` 네임스페이스에 있으며 정책을 위반합니다.

```bash
kubectl create deployment nginx-1 --image=nginx --replicas=6 -n staging
kubectl create deployment nginx-2 --image=nginx --replicas=6
```

클러스터의 모든 디플로이먼트를 조회합니다.

```bash
kubectl get deployments -A

NAMESPACE            NAME                     READY   UP-TO-DATE   AVAILABLE   AGE
default              nginx-2                  6/6     6            6           7m26s
kube-system          coredns                  2/2     2            2           13m
local-path-storage   local-path-provisioner   1/1     1            1           13m
staging              nginx-1                  6/6     6            6           7m44s
```

ValidatingAdmissionPolicy와 그 바인딩을 클러스터의 모든 리소스에 적용합니다.

```bash
kyverno apply /path/to/check-deployment-replicas.yaml --cluster --policy-report
```

다음과 같은 출력이 생성됩니다.

```bash
Applying 1 policy rule(s) to 4 resource(s)...
----------------------------------------------------------------------
POLICY REPORT:
----------------------------------------------------------------------
apiVersion: wgpolicyk8s.io/v1alpha2
kind: ClusterPolicyReport
metadata:
  creationTimestamp: null
  name: merged
results:
- message: 'failed expression: object.spec.replicas <= 5'
  policy: check-deployment-replicas
  resources:
  - apiVersion: apps/v1
    kind: Deployment
    name: nginx-1
    namespace: staging
    uid: a95d1594-44a7-4c8a-9225-04ac34cb9494
  result: fail
  scored: true
  source: kyverno
  timestamp:
    nanos: 0
    seconds: 1707394871
summary:
  error: 0
  fail: 1
  pass: 0
  skip: 0
  warn: 0
```

예상대로 정책은 정책 정의와 바인딩에 모두 일치하는 `nginx-1`에만 적용됩니다.

#### MutatingAdmissionPolicy

마찬가지로 MutatingAdmissionPolicy를 테스트하면 정책이 리소스에 일으킬 변경을 미리 볼 수 있습니다. CLI는 변경이 적용된 최종 리소스를 출력합니다.

##### 예시 1: 기본 변경

예를 들어 ConfigMap에 레이블을 추가하는 MutatingAdmissionPolicy를 테스트할 수 있습니다.

정책 매니페스트(add-label-to-configmap.yaml):

```yaml
apiVersion: admissionregistration.k8s.io/v1alpha1
kind: MutatingAdmissionPolicy
metadata:
  name: 'add-label-to-configmap'
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['configmaps']
  failurePolicy: Fail
  reinvocationPolicy: Never
  mutations:
    - patchType: 'ApplyConfiguration'
      applyConfiguration:
        expression: >
          object.metadata.?labels["lfx-mentorship"].hasValue() ?
              Object{} :
              Object{ metadata: Object.metadata{ labels: {"lfx-mentorship": "kyverno"}}}
```

리소스 매니페스트(configmap.yaml):

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: game-demo
  labels:
    app: game
data:
  player_initial_lives: '3'
```

이제 MutatingAdmissionPolicy를 ConfigMap 리소스에 적용합니다.

```bash
kyverno apply /path/to/add-label-to-configmap.yaml --resource /path/to/configmap.yaml
```

출력에 레이블이 추가된 ConfigMap이 표시됩니다.

```bash
Applying 1 policy rule(s) to 1 resource(s)...

policy add-label-to-configmap applied to default/ConfigMap/game-demo:
apiVersion: v1
data:
  player_initial_lives: "3"
kind: ConfigMap
metadata:
  labels:
    app: game
    lfx-mentorship: kyverno
  name: game-demo
  namespace: default
---

Mutation has been applied successfully.
pass: 1, fail: 0, warn: 0, error: 0, skip: 0
```

출력된 ConfigMap에 새 `lfx-mentorship: kyverno` 레이블이 있으므로, 변경이 올바르게 적용된 것을 확인할 수 있습니다.

##### 예시 2: 바인딩과 네임스페이스 셀렉터를 사용한 변경

MutatingAdmissionPolicyBinding이 포함된 정책으로 정책이 적용될 위치를 제어하는 경우도 테스트할 수 있습니다. 이 예시는 네임스페이스 셀렉터를 사용해 특정 네임스페이스의 ConfigMap에만 정책을 적용합니다.

이를 위해 `values.yaml` 파일을 제공해 리소스가 속한 네임스페이스의 레이블을 시뮬레이션해야 합니다.

정책 매니페스트(add-label-to-configmap.yaml):

이 파일은 레이블을 추가하는 정책과, 그 정책을 `environment: staging` 또는 `environment: production` 레이블이 붙은 네임스페이스로 제한하는 바인딩을 정의합니다.

```yaml
apiVersion: admissionregistration.k8s.io/v1alpha1
kind: MutatingAdmissionPolicy
metadata:
  name: 'add-label-to-configmap'
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['configmaps']
  failurePolicy: Fail
  reinvocationPolicy: Never
  mutations:
    - patchType: 'ApplyConfiguration'
      applyConfiguration:
        expression: >
          object.metadata.?labels["lfx-mentorship"].hasValue() ?
              Object{} :
              Object{ metadata: Object.metadata{ labels: {"lfx-mentorship": "kyverno"}}}
---
apiVersion: admissionregistration.k8s.io/v1alpha1
kind: MutatingAdmissionPolicyBinding
metadata:
  name: 'add-label-to-configmap-binding'
spec:
  policyName: 'add-label-to-configmap'
  matchResources:
    namespaceSelector:
      matchExpressions:
        - key: environment
          operator: In
          values:
            - staging
            - production
```

리소스 매니페스트(configmaps.yaml):

이 파일에는 서로 다른 네임스페이스의 ConfigMap 리소스 세 개가 있습니다. staging과 production의 ConfigMap만 변경되어야 합니다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: matched-cm-1
  namespace: staging
  labels:
    color: red
data:
  player_initial_lives: '3'
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: matched-cm-2
  namespace: production
  labels:
    color: red
data:
  player_initial_lives: '3'
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: unmatched-cm
  namespace: testing
  labels:
    color: blue
data:
  player_initial_lives: '3'
```

값 파일(values.yaml):

이 파일은 필요한 컨텍스트를 제공합니다. staging, production, testing 네임스페이스에 어떤 레이블이 있는지 Kyverno CLI에 알려 주어, 바인딩의 namespaceSelector를 올바르게 평가하게 합니다.

```yaml
apiVersion: cli.kyverno.io/v1alpha1
kind: Value
metadata:
  name: values
namespaceSelector:
  - labels:
      environment: staging
    name: staging
  - labels:
      environment: production
    name: production
  - labels:
      environment: testing
    name: testing
```

이제 MutatingAdmissionPolicy와 그 바인딩을 ConfigMap에 적용합니다.

```bash
kyverno apply /path/to/add-label-to-configmap.yaml --resource /path/to/configmaps.yaml -f /path/to/values.yaml
```

출력에는 staging과 production 네임스페이스의 ConfigMap이 변경된 모습이 나타나고, testing 네임스페이스의 ConfigMap은 그대로입니다.

```bash
Applying 1 policy rule(s) to 3 resource(s)...

policy add-label-to-configmap applied to staging/ConfigMap/matched-cm-1:
apiVersion: v1
data:
  player_initial_lives: "3"
kind: ConfigMap
metadata:
  labels:
    color: red
    lfx-mentorship: kyverno
  name: matched-cm-1
  namespace: staging
---

Mutation has been applied successfully.
policy add-label-to-configmap applied to production/ConfigMap/matched-cm-2:
apiVersion: v1
data:
  player_initial_lives: "3"
kind: ConfigMap
metadata:
  labels:
    color: red
    lfx-mentorship: kyverno
  name: matched-cm-2
  namespace: production
---

Mutation has been applied successfully.
pass: 2, fail: 0, warn: 0, error: 0, skip: 0
```

### ValidatingPolicy 적용

이 예시에서는 `ValidatingPolicy`를 `Deployment` 매니페스트 두 개에 적용합니다. 하나는 정책을 준수하고 다른 하나는 위반합니다.

먼저 모든 `Deployment`의 레플리카가 두 개를 넘지 않도록 하는 `ValidatingPolicy`를 정의합니다.

정책 매니페스트(check-deployment-replicas.yaml):

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-deployment-replicas
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['apps']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['deployments']
  validations:
    - expression: 'object.spec.replicas <= 2'
      message: 'Deployment replicas must be less than or equal to 2'
```

다음은 `Deployment` 매니페스트 두 개입니다. `good-deployment`는 레플리카가 2개로 정책을 준수하고, `bad-deployment`는 3개로 정책을 위반합니다.

리소스 매니페스트(deployments.yaml):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: good-deployment
  labels:
    app: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: bad-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
```

이제 `kyverno apply` 명령으로 두 리소스에 대해 정책을 테스트합니다.

```bash
kyverno apply /path/to/check-deployment-replicas.yaml --resource /path/to/deployments.yaml --policy-report
```

다음과 같은 출력이 생성됩니다.

```bash
apiVersion: openreports.io/v1alpha1
kind: ClusterReport
metadata:
  creationTimestamp: null
  name: merged
results:
- message: Deployment replicas must be less than or equal 2
  policy: check-deployment-replicas
  properties:
    process: background scan
  resources:
  - apiVersion: apps/v1
    kind: Deployment
    name: bad-deployment
    namespace: default
  result: fail
  scored: true
  source: KyvernoValidatingPolicy
  timestamp:
    nanos: 0
    seconds: 1752755472
- message: success
  policy: check-deployment-replicas
  properties:
    process: background scan
  resources:
  - apiVersion: apps/v1
    kind: Deployment
    name: good-deployment
    namespace: default
  result: pass
  scored: true
  source: KyvernoValidatingPolicy
  timestamp:
    nanos: 0
    seconds: 1752755472
source: ""
summary:
  error: 0
  fail: 1
  pass: 1
  skip: 0
  warn: 0
```

로컬 YAML 파일을 테스트하는 것 외에, `kyverno apply` 명령으로 Kubernetes 클러스터에서 이미 실행 중인 리소스에 대해 정책을 검증할 수도 있습니다. `--resource` 플래그로 리소스 파일을 지정하는 대신 `--cluster` 플래그를 사용합니다.

예를 들어 현재 활성 클러스터의 모든 Deployment 리소스에 대해 `check-deployment-replicas` 정책을 테스트하려면 다음을 실행합니다.

```bash
kyverno apply /path/to/check-deployment-replicas.yaml --cluster --policy-report
```

고급 정책 중에는 `resource.Get()` 같은 [Kyverno 커스텀 CEL 함수](/docs/policy-types/validating-policy#kyverno-cel-라이브러리)로 클러스터에 있는 다른 리소스의 상태를 조회하는 것이 많습니다. 이런 정책을 `kyverno apply` 명령으로 로컬에서 테스트할 때는 CLI가 클러스터에 연결해 필요한 리소스를 가져올 수 없으므로, `--context-path` 플래그로 해당 리소스를 입력으로 제공해야 합니다.

이 플래그로 정책이 참조할 리소스를 지정합니다. CLI는 이 리소스를 사용해 정책을 평가합니다.

이 예시는 들어오는 Pod의 이름을 ConfigMap에 저장된 값과 비교해 검증하는 정책을 테스트하는 방법을 보여 줍니다.

먼저 `resource.Get()`으로 `policy-cm`이라는 ConfigMap을 가져오는 `ValidatingPolicy`를 정의합니다. 이 정책은 들어오는 Pod의 이름이 ConfigMap 데이터의 `name` 키와 일치하는지 검증합니다.

정책 매니페스트(check-pod-name-from-configmap.yaml):

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-pod-name-from-configmap
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['pods']
  variables:
    # 이 변수는 Kyverno CEL 함수로 클러스터에서 ConfigMap을 가져옵니다.
    - name: cm
      expression: >-
        resource.Get("v1", "configmaps", object.metadata.namespace, "policy-cm")
  validations:
    # 이 규칙은 Pod의 이름이 ConfigMap 데이터의 'name' 키와 일치하는지 검증합니다.
    - expression: >-
        object.metadata.name == variables.cm.data.name
```

다음으로 Pod 매니페스트 두 개를 정의합니다. 검증을 통과해야 하는 `good-pod`와 실패해야 하는 `bad-pod`입니다.

리소스 매니페스트(pods.yaml):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: good-pod
spec:
  containers:
    - name: nginx
      image: nginx
---
apiVersion: v1
kind: Pod
metadata:
  name: bad-pod
spec:
  containers:
    - name: nginx
      image: nginx
```

CLI는 클러스터에 연결해 `policy-cm` ConfigMap을 가져올 수 없으므로 컨텍스트 파일로 제공해야 합니다. 이 파일에는 로컬 평가 중 `resource.Get()`이 사용할 모의 ConfigMap이 들어 있습니다.

컨텍스트 파일(context.yaml):

```yaml
apiVersion: cli.kyverno.io/v1alpha1
kind: Context
metadata:
  name: context
spec:
  # The resources defined here will be available to functions like resource.Get()
  # 여기에 정의한 리소스는 resource.Get() 같은 함수에서 사용할 수 있습니다.
    - apiVersion: v1
      kind: ConfigMap
      metadata:
        namespace: default
        name: policy-cm
      data:
        # 이 값에 따르면 유효한 파드 이름은 'good-pod'입니다.
        name: good-pod
```

이제 정책, 리소스, 컨텍스트 파일을 지정해 `kyverno apply` 명령을 실행합니다. 결과를 자세히 담은 ClusterReport를 생성하도록 `-p`(또는 `--policy-report`) 플래그도 함께 사용합니다.

```bash
kyverno apply /path/to/policy.yaml --resource /path/to/pods.yaml --context-file /path/to/context.yaml -p
```

다음과 같은 출력이 생성됩니다.

```yaml
apiVersion: openreports.io/v1alpha1
kind: ClusterReport
metadata:
  creationTimestamp: null
  name: merged
results:
  - message: success
    policy: check-pod-name-from-configmap
    properties:
      process: background scan
    resources:
      - apiVersion: v1
        kind: Pod
        name: good-pod
        namespace: default
    result: pass
    scored: true
    source: KyvernoValidatingPolicy
    timestamp:
      nanos: 0
      seconds: 1752756617
  - policy: check-pod-name-from-configmap
    properties:
      process: background scan
    resources:
      - apiVersion: v1
        kind: Pod
        name: bad-pod
        namespace: default
    result: fail
    scored: true
    source: KyvernoValidatingPolicy
    timestamp:
      nanos: 0
      seconds: 1752756617
source: ''
summary:
  error: 0
  fail: 1
  pass: 1
  skip: 0
  warn: 0
```

- `good-pod` 리소스는 이름이 컨텍스트 파일에서 제공한 ConfigMap의 값과 일치하므로 `pass`가 되었습니다.

- `bad-pod` 리소스는 이름이 일치하지 않으므로 `fail`이 되었고, 리포트에 정책의 검증 오류 메시지가 포함됩니다.

`--cluster` 플래그를 사용하면 CLI가 활성 Kubernetes 클러스터에 연결하므로 로컬 컨텍스트 파일이 필요 없습니다. `resource.Get()` 함수가 클러스터에서 실제 ConfigMap을 직접 가져옵니다. 따라서 명령을 실행하기 전에 ConfigMap과 Pod 리소스가 클러스터에 있어야 합니다.

```bash
kyverno apply /path/to/check-pod-name-from-configmap.yaml --cluster --policy-report
```

CEL `ValidatingPolicy`를 `policies.kyverno.io` `PolicyException`과 함께 적용하려면 `--exception` 플래그로 예외 매니페스트를 지정합니다. 그러면 CLI가 정책과 예외를 함께 적용합니다.

이 예시에서는 `hostPath` 볼륨을 허용하지 않는 CEL 정책을 테스트하고, `policies.kyverno.io` `PolicyException`으로 특정 Pod를 예외 처리합니다.

정책 매니페스트(disallow-host-path.yaml):

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: disallow-host-path
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['pods']
  validations:
    - expression: '!has(object.spec.volumes) || object.spec.volumes.all(volume, !has(volume.hostPath))'
      message: 'HostPath volumes are forbidden. The field spec.volumes[*].hostPath must be unset.'
```

다음으로 `hostPath` 볼륨을 마운트해 이 정책을 명백히 위반하는 Pod를 정의합니다. 예외가 없으면 이 Pod는 차단됩니다.

리소스 매니페스트(pod-with-hostpath.yaml):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-hostpath
spec:
  containers:
    - name: nginx
      image: nginx
  volumes:
    - name: udev
      hostPath:
        path: /etc/udev
```

이제 특정 Pod를 정책에서 제외하는 CEL `PolicyException`을 만듭니다. 이 예외는 Pod를 이름으로 매칭하며 `disallow-host-path` 정책을 참조합니다.

정책 예외 매니페스트(exception.yaml):

```yaml
apiVersion: policies.kyverno.io/v1
kind: PolicyException
metadata:
  name: exempt-hostpath-pod
spec:
  policyRefs:
    - name: disallow-host-path
      kind: ValidatingPolicy
  matchConditions:
    - name: 'skip-pod-by-name'
      expression: "object.metadata.name == 'pod-with-hostpath'"
```

이제 `kyverno apply` 명령에 정책, 리소스, `--exception` 플래그로 지정한 예외를 함께 제공합니다. 자세한 리포트를 생성하도록 `-p`도 사용합니다.

```bash
kyverno apply policy.yaml --resource resource.yaml --exception exception.yaml -p
```

다음과 같은 출력이 생성됩니다.

```yaml
apiVersion: openreports.io/v1alpha1
kind: ClusterReport
metadata:
  creationTimestamp: null
  name: merged
results:
  - message: 'rule is skipped due to policy exception: exempt-hostpath-pod'
    policy: disallow-host-path
    properties:
      exceptions: exempt-hostpath-pod
      process: background scan
    resources:
      - apiVersion: v1
        kind: Pod
        name: pod-with-hostpath
        namespace: default
    result: skip
    rule: exception
    scored: true
    source: KyvernoValidatingPolicy
    timestamp:
      nanos: 0
      seconds: 1752759828
source: ''
summary:
  error: 0
  fail: 0
  pass: 0
  skip: 1
  warn: 0
```

출력을 보면 CEL PolicyException이 의도대로 동작했음을 알 수 있습니다.

- `result: skip`: 정책 규칙이 리소스에 강제되지 않았습니다.

- `properties.exceptions: exempt-hostpath-pod`: 리포트가 건너뛰기를 일으킨 CEL PolicyException을 명시적으로 보여 줍니다.

- `summary.skip: 1`: 최종 집계에 규칙 하나가 건너뛰어졌다고 반영됩니다.

### 정책 결정 설명

<FeatureState state="alpha" version="v1.20" />

`--explain` 플래그는 각 CEL 정책과 리소스에 대해 정책이 결과에 이른 과정을 출력합니다. 정책이 리소스에 적용되었는지, 각 매치 조건과 변수가 무엇으로 평가되었는지, 각 검증의 결과가 무엇인지를 보여 줍니다. 통과하지 못한 검사는 결과를 가른 표현식 각 부분의 값도 보여 줍니다. 결과, 요약, 종료 코드는 바뀌지 않습니다.

`--explain`은 `ValidatingPolicy`, `MutatingPolicy`, `GeneratingPolicy`, `DeletingPolicy`, `ImageValidatingPolicy`에서 지원됩니다.

```sh
kyverno apply /path/to/policy.yaml --resource /path/to/resource.yaml --explain
```

예를 들어 다음 `ValidatingPolicy`는 파드의 `containers`에 `team`과 `app` 레이블이 있고 `:latest` 이미지가 없어야 하며, `kube-system` 네임스페이스는 건너뜁니다.

정책 매니페스트(require-team-and-app.yaml):

```yaml
apiVersion: policies.kyverno.io/v1beta1
kind: ValidatingPolicy
metadata:
  name: require-team-and-app
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['pods']
  matchConditions:
    - name: not-kube-system
      expression: "object.metadata.namespace != 'kube-system'"
  variables:
    - name: labels
      expression: 'object.metadata.?labels.orValue({})'
  validations:
    - expression: "'team' in variables.labels"
      message: 'every pod needs a team label'
    - expression: "'app' in variables.labels"
      message: 'every pod needs an app label'
    - expression: "!object.spec.containers.exists(c, c.image.endsWith(':latest'))"
      message: 'images must not use the latest tag'
```

리소스 매니페스트(pods.yaml):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: good-pod
  namespace: prod
  labels:
    team: payments
    app: api
spec:
  containers:
    - name: api
      image: nginx:1.27
---
apiVersion: v1
kind: Pod
metadata:
  name: missing-app
  namespace: prod
  labels:
    team: payments
spec:
  containers:
    - name: api
      image: nginx:1.27
---
apiVersion: v1
kind: Pod
metadata:
  name: system-pod
  namespace: kube-system
spec:
  containers:
    - name: dns
      image: coredns:1.11
```

```sh
kyverno apply require-team-and-app.yaml --resource pods.yaml --explain
```

추적 결과의 각 줄은 Kyverno가 평가하는 순서에 따라 결정의 한 계층에 해당합니다.

| 계층 | 설명 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SCOPE` | 정책의 `matchConstraints`가 리소스를 선택하는지(`applied`) 아닌지(`skipped`), 선택하지 않는다면 어떤 제약이 제외했는지 보여 줍니다. JSON 페이로드(`--json`)에서는 `matchConstraints`를 확인하지 않으므로 범위가 `applied`이며, 이유는 `evaluated against a JSON payload, so no matchConstraints apply`입니다. |
| `MATCH` | 각 매치 조건과 그 결과입니다. `DeletingPolicy`는 `conditions`를 보여 줍니다. |
| `VARIABLES` | 정책이 읽은 각 변수와 그 값입니다. |
| `IMAGES` | `ImageValidatingPolicy`에서 리소스에 있는 각 이미지와, `matchImageReferences`가 그 이미지를 검사 대상으로 선택했는지(`checked`) 아닌지(`skipped`)를 보여 줍니다. |
| `VALIDATION` | 각 검증과 그 결과입니다. 검증은 순서대로 실행되며 통과하지 못한 첫 검증에서 멈추므로, 그 뒤의 검증은 `NOT RUN`으로 표시됩니다. |
| `MUTATIONS` | `MutatingPolicy`에서 실행된 각 변경과 그 결과물입니다. |
| `GENERATE` | `GeneratingPolicy`에서 각 생성 항목과 생성된 리소스입니다. |
| `VERDICT` | 결과인 `PASS`, `FAIL`, `ERROR`, `SKIP`과 메시지입니다. `PASS`가 아닌 결과를 표현식이 결정했다면, 세부 분해가 없는 경우(아래 참고)를 제외하고 `evaluated:` 줄이 그 표현식 각 부분의 값을 보여 줍니다. `SCOPE`나 매치 조건 때문에 생긴 `SKIP`에는 `evaluated:` 줄이 없습니다. |

`DeletingPolicy`에서 `PASS`는 리소스가 삭제된다는 뜻이고, `FAIL`은 리소스가 유지된다는 뜻입니다.

:::caution[민감한 값]
추적 결과에는 리소스 필드와 변수 등 표현식이 읽은 값이 출력됩니다. Secret의 `data`를 읽는 정책이라면 그 데이터가 출력됩니다. CI 로그에 남기거나 다른 사람과 공유할 때처럼, 출력을 민감한 정보로 다루세요.
:::

`--explain`은 출력이 기계가 읽을 수 있는 형태여야 하는 `--policy-report`, `--generate-exceptions`, `--stdin`과 함께 사용할 수 없습니다.

일부 값은 표시되지 않습니다.

- `all()`, `exists()`, `map()`, `filter()` 같은 루프 안에서는 CEL이 마지막 항목의 값만 유지합니다. 그래서 엉뚱한 항목의 값을 보여 주지 않도록 루프 안의 값은 생략합니다. 생략한 경우 추적 결과에 그 사실이 표시됩니다.
- `ImageValidatingPolicy`에서 이미지를 검증하는 표현식(`verifyImageSignatures`, `verifyAttestationSignatures`, `getImageData`, `extractPayload`)은 결과만 보여 주고 세부 분해는 보여 주지 않습니다. 설명을 위해 검증을 두 번째로 실행하는 일은 없기 때문입니다. 실패 메시지에는 대신 검증 세부 정보가 포함됩니다.
- 평가 밖의 대상에 접근하거나 호출할 때마다 다른 값을 반환하는 함수(`http.Get`, `http.Post`, `resource.Get`, `resource.List`, `resource.Post`, `image.GetMetadata`, `random()`, `time.now()`)를 호출하는 표현식은 결과만 보여 주고 세부 분해는 보여 주지 않습니다. `--explain`은 이런 함수를 두 번째로 호출하지 않기 때문입니다. 예를 들어 `http.Post`는 여전히 한 번만 전송됩니다. `ValidatingPolicy`, `MutatingPolicy`, `ImageValidatingPolicy`에서는 추적 결과에 호출을 명시합니다: `(no breakdown: it calls http.Post, which is not run a second time)`.
- `GeneratingPolicy`에서 `template` 항목은 생성한 리소스를 보여 주지만, 각 플레이스홀더의 값은 보여 주지 않습니다.
- 정책의 `matchConstraints`가 선택하지 않는 리소스는 `SCOPE skipped`로 표시되지만, `--explain`을 쓰지 않을 때와 마찬가지로 요약에는 집계되지 않습니다.

## Test 명령

`test` 명령은 리소스 매니페스트에 대해 정책 동작을 평가하고, 그 결과를 `kyverno-test.yaml` 파일에 선언한 기대 결과와 비교합니다. 로컬 디렉터리나 Git 저장소에서 테스트 매니페스트를 찾아, 함께 놓인 정책 파일과 리소스 파일로 각 테스트를 실행합니다.

Kyverno CLI 테스트는 `ValidatingPolicy`를 포함한 CEL 기반 Kyverno 정책과, `ValidatingAdmissionPolicy`, `MutatingAdmissionPolicy`를 포함한 Kubernetes 네이티브 어드미션 정책을 지원합니다. 자세한 결과를 보려면 `--detailed-results`를 사용하고, 플래그와 사용법은 `-h`로 확인하세요.

### 테스트 파일 구조

테스트 매니페스트는 평가할 정책과 리소스, 선택 사항인 테스트 컨텍스트나 CEL 정책 예외, 기대 결과를 지정합니다. 예를 들면 다음과 같습니다.

```yaml
apiVersion: cli.kyverno.io/v1alpha1
kind: Test
metadata:
  name: kyverno-test
policies:
  - policy.yaml
resources:
  - resources.yaml
context: context.yaml # 선택 사항: CEL 리소스 조회용 모의 리소스
variables: values.yaml # 선택 사항: 모의 네임스페이스 오브젝트 같은 CEL 테스트 값
exceptions: # 선택 사항: CEL ValidatingPolicy용 PolicyException 매니페스트
  - exception.yaml
apiCallResponses: # 선택 사항: CEL http.Get()/http.Post()용 오프라인 HTTP 모의 응답
  - url: https://example.com/api
    method: GET
    response:
      statusCode: 200
      body:
        allowed: true
globalContextEntries: # 선택 사항: CEL globalContext.Get()용 모의 데이터
  - name: config
    data:
      allowed: true
results:
  - isValidatingPolicy: true # Kyverno CEL ValidatingPolicy에 설정
    policy: check-policy
    kind: Pod
    resources:
      - default/example
    result: pass
  - isValidatingAdmissionPolicy: true # Kubernetes ValidatingAdmissionPolicy에 설정
    policy: check-native-policy
    kind: Pod
    resources:
      - default/example
    result: pass
```

네이티브 `ValidatingAdmissionPolicy` 테스트에서는 해당 결과에 `isValidatingAdmissionPolicy: true`를 설정합니다. Kyverno CEL `ValidatingPolicy` 테스트에서는 `isValidatingPolicy: true`를 설정합니다. 전체 테스트 매니페스트는 아래 예시를 참고하세요.

### 로컬 파일로 테스트

작업 디렉터리의 로컬 파일 집합을 테스트합니다.

```sh
kyverno test .
```

디렉터리를 지정해 로컬 파일 집합을 테스트합니다.

```sh
kyverno test /path/to/folderContainingTestYamls
```

### Git 저장소로 테스트

URL을 지정해 Git 저장소 전체를 테스트합니다. 브랜치를 지정하지 않으면 기본값은 `main`입니다.

```sh
kyverno test https://github.com/owner/repository
```

저장소 URL에 디렉터리를 지정하고 `--git-branch` 또는 `-b` 플래그로 브랜치를 지정하면 저장소의 특정 디렉터리를 테스트합니다. `main`을 테스트하더라도 저장소 URL에 디렉터리를 쓰면 `--git-branch` 또는 `-b` 플래그를 반드시 전달해야 합니다.

```sh
kyverno test https://github.com/owner/repository/path/to/tests -b branch-name
```

`-f` 플래그로 테스트 케이스가 담긴 파일 이름을 직접 지정합니다. 기본적으로 `test`는 `kyverno-test.yaml`이라는 파일을 찾습니다.

### 이미지 레지스트리에 접근하는 정책 테스트

컨텍스트 변수를 설정하려고 이미지 레지스트리에 접근해야 하는 CEL 정책의 경우, 그 변수를 값 파일에서 가져오거나 `--registry` 플래그를 전달해 실제 레지스트리에서 가져올 수 있습니다.

### 리소스 일부만 테스트

테스트 매니페스트의 정책과 리소스 조합 중 일부만 테스트하고 싶을 때가 있습니다. 이때 `--test-case-selector` 플래그로 실행할 테스트를 정확히 지정합니다.

```sh
kyverno test . --test-case-selector "policy=check-deployment-replicas, resource=nginx-demo"
```

일부 정책은 리소스가 생성되는 네임스페이스의 레이블이나 이름 같은 속성을 보고 판단해야 합니다. CEL의 `namespaceObject` 변수는 이를 위해 전체 네임스페이스 오브젝트에 접근하게 해 줍니다.

`kyverno test`를 실행하면 명령이 오프라인 모드로 동작하며 실제 클러스터의 네임스페이스에 접근할 수 없습니다. `namespaceObject`를 사용하는 정책을 테스트하려면 모의 네임스페이스 정의를 제공해야 합니다. "값 파일"을 만들어 `kyverno-test.yaml`에서 참조하면 됩니다.

`default` 네임스페이스에 특정 Deployment를 만들지 못하게 하는 정책부터 시작합니다. 이 정책은 `namespaceObject.metadata.name`으로 네임스페이스 이름을 확인합니다.

정책 매니페스트(`disallow-default-deployment.yaml`):

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-deployment-namespace
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['apps']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['deployments']
    # 이 정책은 `app: nginx` 레이블이 있는 Deployment에만 적용됩니다.
    objectSelector:
      matchLabels:
        app: nginx
  validations:
    # 검증 로직은 Namespace 오브젝트의 이름을 확인합니다.
    - expression: "namespaceObject.metadata.name != 'default'"
      message: "Using 'default' namespace is not allowed for this application."
```

1. `default` 네임스페이스의 Deployment(실패해야 함).
2. 다른 네임스페이스인 `staging`의 Deployment(통과해야 함).
3. `app: nginx` 레이블이 없는 Deployment 두 개(건너뛰어야 함).

`kyverno test`로 오프라인 테스트를 할 때는 `resource.Get()` 함수가 정상적으로 처리되도록 이 외부 리소스를 "컨텍스트"로 제공해야 합니다. `kyverno-test.yaml`에서 컨텍스트 파일을 직접 참조하면 됩니다.

이 예시에서는 Pod의 이름을 ConfigMap에 저장된 값과 비교해 검증하는 정책을 테스트합니다.

먼저 `check-pod-name-from-configmap`이라는 정책을 정의합니다. 이 정책은 `resource.Get()`으로 `policy-cm`이라는 ConfigMap을 가져온 뒤, 들어오는 Pod의 이름이 ConfigMap 데이터의 `name` 키와 일치하는지 확인합니다.

정책 매니페스트(`check-pod-name-from-configmap.yaml`):

```yaml
# policy.yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-pod-name-from-configmap
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['pods']
  variables:
    # Pod의 네임스페이스에서 ConfigMap 'policy-cm'을 가져옵니다.
    - name: cm
      expression: >-
        resource.Get("v1", "configmaps", object.metadata.namespace, "policy-cm")
  validations:
    # Pod의 이름이 ConfigMap의 값과 일치할 때만 유효합니다.
    - expression: >-
        object.metadata.name == variables.cm.data.name
```

### 오프라인 HTTP 모의와 글로벌 컨텍스트로 정책 테스트

`http.Get()`이나 `http.Post()`로 외부 HTTP 서비스를 호출하거나 `GlobalContextEntry`를 조회하는 CEL 정책은 `kyverno test`로 오프라인에서 테스트할 수 있습니다. Kyverno CLI v1.14부터 `kyverno-test.yaml`은 선택 필드 `apiCallResponses`와 `globalContextEntries`를 받습니다. 이 필드로 기대하는 외부 데이터를 인라인으로 선언해 로컬 개발과 CI/CD 파이프라인에서 사용할 수 있습니다.

#### 스키마 개요

```yaml
apiVersion: cli.kyverno.io/v1alpha1
kind: Test
metadata:
  name: my-test
policies:
  - policy.yaml
resources:
  - resources.yaml
# CEL http.Get() / http.Post() 호출에 대한 인라인 모의 응답.
apiCallResponses:
  - url: https://external-service.example.com/api/check # 매칭할 URL(필수)
    method: GET # HTTP 메서드(선택 사항. 생략하면 모든 메서드에 매칭)
    response:
      statusCode: 200 # 유효한 HTTP 상태 코드여야 함(100–599)
      body: # 임의의 JSON 오브젝트
        allowed: true
# GlobalContextEntry 참조용 인라인 모의 데이터.
# 각 항목에는 data, resources, resourceFiles 중 정확히 하나가 필요합니다(상호 배타적).
globalContextEntries:
  - name: gctxentry-deployments # 정책에서 사용하는 GlobalContextEntry 이름과 일치해야 함
    # 옵션 1: 임의의 JSON 루트 값
    data:
      deployments:
        - name: existing-deployment-1
        - name: existing-deployment-2
    # 옵션 2: 인라인 Kubernetes 리소스 매니페스트(kubernetesResource 캐시 형태를 모방)
    # resources:
    #   - apiVersion: apps/v1
    #     kind: Deployment
    #     metadata:
    #       name: existing-deployment-1
    #       namespace: default
    # 옵션 3: 테스트 디렉터리 기준 YAML 파일 경로
    # resourceFiles:
    #   - gce-deployments.yaml
results:
  - kind: Pod
    isValidatingPolicy: true
    policy: my-policy
    resources:
      - default/my-pod
    result: pass
```

:::note[참고]
각 `apiCallResponses` 항목의 `body` 필드에는 유효한 JSON 값(오브젝트, 배열, 문자열, 숫자, 불리언, null)을 모두 쓸 수 있습니다. 상태 코드가 표준 HTTP 코드(100–599)인지, 본문이 유효한 JSON인지 검증하며, 모의 응답 형식이 잘못되었으면 CLI가 테스트를 실행하기 전에 오류를 보고합니다.
:::

:::note[상호 배타성]
각 `globalContextEntries` 항목에서 `data`, `resources`, `resourceFiles`는 서로 배타적이므로 정확히 하나만 지정하세요. 임의의 JSON에는 `data`를, Kubernetes 매니페스트에는 `resources`나 `resourceFiles`를 사용합니다.
:::

:::note[중복 키 검증]
각 `apiCallResponses` 항목은 **메서드 + URL** 조합으로 고유하게 식별됩니다. `method`와 `url`이 같은 항목을 둘 이상 설정하면 오류이며, CLI가 평가를 시작하기 전에 테스트 매니페스트를 거부합니다. 중복된 모의 응답 때문에 조용히 비결정적으로 동작하는 문제를 막기 위해서입니다.

같은 URL에 대한 서로 다른 HTTP 메서드는 별개의 유효한 항목입니다. 예를 들어 둘 다 `https://authz.example.com/validate`를 가리키는 `GET` 항목과 `POST` 항목은 충돌 없이 함께 쓸 수 있습니다.
:::

다음 예시는 Kyverno의 CEL `http.Post()` 라이브러리 함수로 외부 인가 서비스를 호출하는 `ValidatingPolicy`를 테스트합니다. 통과 시나리오(서비스가 요청을 허용)와 거부 시나리오(서비스가 요청을 거부)를 모두 보여 줍니다.

정책 매니페스트(`policy.yaml`):

```yaml

    resourceRules:
      - apiGroups: ['']

```

#### CEL 정책용 GlobalContextEntry 데이터 모의

`globalContextEntries` 필드는 `globalContext.Get()`을 호출하는 CEL 정책에 오프라인 데이터를 제공합니다. 항목마다 임의의 JSON은 `data`로, Kubernetes 매니페스트는 `resources`로, 픽스처 파일 경로는 `resourceFiles`로 선언합니다. 이 소스들은 상호 배타적입니다.

예를 들어 `ValidatingPolicy`가 모의 Deployment 컬렉션을 읽을 수 있습니다.

정책 매니페스트(`policy.yaml`):

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-deployment-count
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: [apps]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [deployments]
  variables:
    - name: deploymentData
      expression: globalContext.Get("gctxentry-deployments", "")
  validations:
    - expression: >-
        variables.deploymentData != null && size(variables.deploymentData.deployments) >= 2
      message: 'At least two deployments must be present in global context'
```

테스트 매니페스트(`kyverno-test.yaml`):

```yaml
apiVersion: cli.kyverno.io/v1alpha1
kind: Test
metadata:
  name: mock-global-context
policies:
  - policy.yaml
resources:
  - resources.yaml
globalContextEntries:
  - name: gctxentry-deployments
    data:
      deployments:
        - name: existing-deployment-1
        - name: existing-deployment-2
results:
  - isValidatingPolicy: true
    kind: Deployment
    policy: check-deployment-count
    resources:
      - test-ns/test-deployment
    result: pass
```

더 큰 픽스처에는 `data` 대신 `resourceFiles`로 상대 경로의 YAML 매니페스트를 나열하거나, `resources`로 인라인 정의하세요. 정책의 CEL 표현식은 선택한 소스가 제공하는 데이터 형태에 맞게 읽어야 합니다.

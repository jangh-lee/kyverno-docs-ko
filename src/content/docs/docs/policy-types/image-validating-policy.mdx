Kyverno `ImageValidatingPolicy`는 컨테이너 이미지 서명과 증명(attestation)을 확인하기 위해 만든 정책 유형이다.

## 추가 필드

`ImageValidatingPolicy`는 [Kyverno ValidatingPolicy](/docs/policy-types/validating-policy)에 이미지 검증용 필드를 더했다. 전체 레퍼런스는 [API 명세](https://htmlpreview.github.io/?https://github.com/kyverno/kyverno/blob/main/docs/user/crd/index.html#policies.kyverno.io/v1.ImageValidatingPolicy)에서 볼 수 있다.

### images

`Kubernetes` 리소스를 평가할 때는 파드와 파드 템플릿의 이미지를 자동으로 추출해 처리한다. 사용자 정의 리소스나 `JSON` 페이로드는 `images` 필드에 CEL 표현식을 선언해 페이로드에서 이미지를 추출한다.

예를 들어 아래 정책은 `imageReference` 필드에 지정된 이미지를 처리한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: sample
spec:
  evaluation:
    mode: JSON
  images:
    - name: imagerefs
      expression: '[object.imageReference]'
  # ...
```

### matchImageReferences

`spec.matchImageReferences` 필드는 컨테이너 이미지를 매칭하는 규칙을 정의한다. 정책이 어떤 이미지에 적용될지를 glob 패턴이나 CEL 표현식으로 지정할 수 있다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchImageReferences: # 하위 필드가 하나 이상 필요하다
    - glob: 'ghcr.io/kyverno/*' # glob 패턴으로 이미지 매칭
    - expression: "image.registry == 'ghcr.io'" # CEL 표현식으로 매칭
  # ...
```

### attestors

`attestors` 필드는 키나 인증서 같은 신뢰할 수 있는 서명 주체를 선언한다.

**Cosign attestor:** 이미지 검증에 공개 키, 키리스(keyless) 서명, 투명성 로그, 인증서, TUF 기반 메타데이터를 사용한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['pods']
  variables:
    - name: cm
      expression: >-
        resource.Get("v1", "configmaps", object.metadata.namespace, "keys")
  attestors:
    - name: cosign # 이 attestor를 식별하는 고유 이름
      cosign:
        key: # 공개 키 기반 검증. 하위 필드가 하나 이상 필요하다
          expression: variables.cm.data.pubKey # 공개 키로 평가되는 CEL 표현식
          kms: 'gcpkms://...' # 키 검증용 KMS URI (예: GCP KMS, AWS KMS)
          hashAlgorithm: 'sha256' # 키와 함께 쓰는 해시 알고리즘 (선택)
          data:
            | # 공개 키를 직접 넣는 인라인 데이터 (secretRef나 kms를 쓰면 생략 가능)
            -----BEGIN PUBLIC KEY-----
            ...
            -----END PUBLIC KEY-----

        keyless: # 키리스 서명 검증 (OIDC 기반)
          identities: # 허용할 서명 신원 목록
            - subject: 'https://github.com/myorg/myrepo/.github/workflows/deploy.yaml@refs/heads/main'
              issuer: 'https://token.actions.githubusercontent.com'
              subjectRegExp: ".*github\\.com/.*/.*/.github/workflows/.*" # subject를 정규식으로 매칭 (선택)
              issuerRegExp: "https://token\\.actions\\.githubusercontent\\.com" # issuer를 정규식으로 매칭 (선택)
          trustedRoot:
            expression: variables.githubTrustedRoot # 신뢰 루트 JSON으로 평가되는 CEL 표현식
          roots:
            | # PEM 인코딩된 신뢰 루트 인증서 집합 (선택). 지정하지 않으면 시스템 루트를 사용한다.
            -----BEGIN CERTIFICATE-----
            ...
            -----END CERTIFICATE-----

        ctlog: # 투명성 로그 설정 (예: Rekor)
          url: 'https://rekor.sigstore.dev'
          rekorPubKey: | # Rekor 항목을 검증하는 공개 키
            -----BEGIN PUBLIC KEY-----
            ...
            -----END PUBLIC KEY-----
          ctLogPubKey: | # CT 로그 항목을 검증하는 공개 키 (선택)
            -----BEGIN PUBLIC KEY-----
            ...
            -----END PUBLIC KEY-----
          tsaCertChain:
            | # 타임스탬프 기관(TSA)의 인증서 체인 (선택)
            -----BEGIN CERTIFICATE-----
            ...
            -----END CERTIFICATE-----
          insecureIgnoreTlog: false # TLog 검증 건너뛰기 (테스트 전용)
          insecureIgnoreSCT: false # SCT(Signed Certificate Timestamp) 검증 건너뛰기 (테스트 전용)

        certificate: # 인증서 기반 검증. 하위 필드가 하나 이상 필요하다
          cert:
            value: | # 인라인 서명 인증서
              -----BEGIN CERTIFICATE-----
              ...
              -----END CERTIFICATE-----
            expression: variables.cm.data.cert # 인증서로 평가되는 CEL 표현식
          certChain: # 하위 필드가 하나 이상 필요하다
            value: | # 서명자와 연결된 인증서 체인
              -----BEGIN CERTIFICATE-----
              ...
              -----END CERTIFICATE-----
            expression: variables.cm.data.certChain # 인증서로 평가되는 CEL 표현식

        source: # 이미지 출처를 제한하는 메타데이터 (선택)
          repository: 'ghcr.io/myorg/myimage' # 특정 이미지 리포지토리로 제한
          PullSecrets: # 레지스트리 접근에 쓰는 Kubernetes 시크릿
            - name: my-registry-secret
          tagPrefix: 'v1.' # 이 접두사로 시작하는 태그의 이미지만 검증

        tuf:
          root:
            path: '/var/run/tuf/root.json' # TUF 루트 메타데이터의 로컬 경로 (선택)
            data: | # base64로 인코딩한 TUF 루트 메타데이터 (선택)
              eyJzaWduZWQiOiB7Li4ufSwgInNpZ25hdHVyZXMiOiBbLi4uXX0=
          mirror: 'https://tuf.example.org' # Sigstore TUF 미러 URL (선택)

  # ...
```

**Notary attestor:** 이미지 서명 검증에 인증서와, 선택적으로 타임스탬프 기관(TSA) 인증서를 사용한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchConstraints:
    resourceRules:
      - apiGroups:
          - ''
        apiVersions:
          - v1
        operations:
          - CREATE
        resources:
          - pods
  variables:
    - name: cm
      expression: 'resource.Get("v1", "configmaps", object.metadata.namespace, "keys")'
  matchImageReferences:
    - glob: ghcr.io/*
  attestors:
    - name: notary
      notary:
        certs:
          value: |
            -----BEGIN CERTIFICATE-----
            MIIBjTCCATOgAwIBAgIUdMiN3gC...
            -----END CERTIFICATE-----
          expression: variables.cm.data.cert
        tsaCerts:
          value: |
            -----BEGIN CERTIFICATE-----
            MIIC4jCCAcqgAwIBAgIQAm3T2tWk...
            -----END CERTIFICATE-----
          expression: variables.cm.data.tsaCert
```

### attestations

`attestations` 필드는 추가로 검증할 메타데이터를 지정한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['pods']
  matchImageReferences:
    - glob: ghcr.io/*
  attestors:
    - name: notary
      notary:
        certs:
          value: |-
            -----BEGIN CERTIFICATE-----
            MIIBjTCCATOgAwIBAgIUdMiN3gC...
            -----END CERTIFICATE-----
  attestations:
    - name: sbom # 이 증명의 논리적 이름
      referrer: # 검증에 OCI 아티팩트 유형을 사용한다
        type: sbom/cyclone-dx

    - name: toto # `toto`라는 이름의 또 다른 증명
      intoto:
        type: https://example.com/attestations/slsa-provenance/v0.2 # in-toto 형식의 predicate 유형 URI
```

### validationConfigurations

`validationConfigurations` 필드는 이미지 태그를 다이제스트로 변경할지, 이미지가 다이제스트를 쓰는지 확인할지, 정책 전반에서 이미지 검증을 강제할지를 설정한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchImageReferences:
    - glob: ghcr.io/*
  validationConfigurations:
    mutateDigest: true # 이미지 태그를 다이제스트로 변경한다 (가변 태그를 피하려면 권장).
    required: true # 이미지가 정책에 따라 반드시 검증되도록 강제한다.
    verifyDigest: true # 태그가 아니라 다이제스트로 이미지를 검증한다.
```

### credentials

`credentials`는 프라이빗 레지스트리에 안전하게 접근하는 데 필요한 인증 정보를 지정한다. 이 필드는 두 가지 방식을 지원한다. 하나는 클라우드 환경 자격 증명을 쓰는 **providers**이고, 다른 하나는 레지스트리 로그인 정보가 든 쿠버네티스 **secrets**이다.

:::caution[전역 자격 증명 헬퍼는 없다]
`--registryCredentialHelpers` Helm/CLI 플래그(예: `features.registryCredentialHelpers.enabled`)는 `ImageValidatingPolicy`에 **아무런 영향도 주지 않는다**. IVPOL의 레지스트리 인증은 각 정책의 `spec.credentials`로만 설정할 수 있으며, 전역 폴백(fallback)은 없다.
:::

#### 알려진 제약

`ImageValidatingPolicy`는 아래 자격 증명 기능을 **아직 지원하지 않는다**.

- **파드 `imagePullSecrets` 자동 인식 불가**: IVPOL은 어드미션 대상 파드/디플로이먼트(Deployment)에 선언된 `imagePullSecrets`를 자동으로 가져오지 않는다. 시크릿(Secret)은 `spec.credentials.secrets`에 직접 나열해야 한다.
- **다른 네임스페이스의 시크릿 사용 불가**: 시크릿은 Kyverno 네임스페이스(보통 `kyverno`)에 있어야 한다. `namespace/name` 표기는 지원하지 않으므로 시크릿을 Kyverno 네임스페이스로 복사하거나 동기화해야 한다.
- **전역 자격 증명 헬퍼 없음**: providers는 정책마다 선언해야 한다(위 설명 참고).

#### providers

`providers` 필드는 클라우드 환경에 이미 설정된 자격 증명 헬퍼를 켠다. 각 값은 해당 자격 증명 헬퍼를 레지스트리 인증에 사용하도록 활성화한다.

| Provider  | 레지스트리                                        | 일반적인 인증 방식                   |
| --------- | ------------------------------------------------- | ------------------------------------ |
| `default` | 도커 자격 증명 헬퍼를 지원하는 모든 레지스트리  | Docker config / 키체인               |
| `amazon`  | Amazon ECR (`*.dkr.ecr.*.amazonaws.com`)          | IRSA / IAM 인스턴스 프로파일         |
| `google`  | Google Artifact Registry / GCR                    | Workload Identity / ADC              |
| `azure`   | Azure Container Registry                          | Workload Identity / 관리형 ID        |
| `github`  | GitHub Container Registry (`ghcr.io`)             | 자격 증명 헬퍼를 통한 GitHub 토큰    |

클라우드 IAM(AWS의 IRSA, GKE의 Workload Identity 등)을 쓴다면, Kyverno 어드미션 컨트롤러 파드에 적절한 IAM 권한이 있는 한 맞는 provider만 추가하면 된다. 시크릿은 필요 없다.

#### secrets

`secrets` 필드에는 프라이빗 레지스트리 인증에 쓸 쿠버네티스 `Secret`(`kubernetes.io/dockerconfigjson` 유형) 이름을 목록으로 넣는다.

:::caution[시크릿은 Kyverno 네임스페이스에 있어야 한다]
시크릿은 어드미션 대상 리소스의 네임스페이스가 아니라 **Kyverno 네임스페이스**(보통 `kyverno`)에 있어야 한다. IVPOL은 파드 스펙의 `imagePullSecrets`를 읽지 않고, 네임스페이스를 넘나드는 참조(`namespace/name`)도 지원하지 않는다. 레지스트리 시크릿이 워크로드 네임스페이스에 있다면 Kyverno 네임스페이스로 복사하거나 동기화한다.
:::

#### 예시: 퍼블릭 레지스트리 (자격 증명 불필요)

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchImageReferences:
    - glob: ghcr.io/*
  # 퍼블릭 레지스트리에는 credentials 블록이 필요 없다
```

#### 예시: IRSA를 쓰는 Amazon ECR

Kyverno 어드미션 컨트롤러 서비스어카운트(ServiceAccount)에 `ecr:GetAuthorizationToken`, `ecr:BatchGetImage` 권한이 있는 IAM 역할을 연결하고, `AWS_ROLE_ARN`과 `AWS_WEB_IDENTITY_TOKEN_FILE`이 파드에 주입되는지 확인한다. 그런 다음 정책에 `providers: [amazon]`을 설정한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: verify-ecr-images
spec:
  matchImageReferences:
    - glob: '123456789.dkr.ecr.eu-central-1.amazonaws.com/*'
  credentials:
    providers:
      - amazon
  attestors:
    - name: cosign
      cosign:
        key:
          data: |
            -----BEGIN PUBLIC KEY-----
            ...
            -----END PUBLIC KEY-----
  validations:
    - expression: >-
        images.containers.map(image, verifyImageSignatures(image, [attestors.cosign])).all(e, e > 0)
      message: image must be signed
```

#### 예시: 풀 시크릿을 쓰는 프라이빗 레지스트리

여기서 참조하기 전에 Kyverno 네임스페이스에 시크릿을 먼저 만들어야 한다.

```bash
kubectl create secret docker-registry my-registry-secret \
  --docker-server=registry.example.com \
  --docker-username=<user> \
  --docker-password=<token> \
  -n kyverno
```

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: verify-private-images
spec:
  matchImageReferences:
    - glob: 'registry.example.com/*'
  credentials:
    secrets:
      - my-registry-secret # Kyverno 네임스페이스에 있어야 한다
  attestors:
    - name: notary
      notary:
        certs:
          value: |
            -----BEGIN CERTIFICATE-----
            ...
            -----END CERTIFICATE-----
  validations:
    - expression: >-
        images.containers.map(image, verifyImageSignatures(image, [attestors.notary])).all(e, e > 0)
      message: image must be signed
```

#### 예시: providers와 secrets 함께 쓰기

인증 방식이 서로 다른 여러 레지스트리의 이미지를 한 정책에서 검증해야 한다면 두 방식을 함께 쓸 수 있다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchImageReferences:
    - glob: '*.dkr.ecr.*.amazonaws.com/*'
    - glob: 'registry.example.com/*'
  credentials:
    providers:
      - amazon
    secrets:
      - my-registry-secret # Kyverno 네임스페이스에 있어야 한다
```

## CEL 라이브러리

Kyverno는 Kubernetes의 CEL 환경에 라이브러리를 더해 복잡한 정책 로직과 이미지 검증용 고급 기능을 쓸 수 있게 한다. 공통 [Kyverno CEL 라이브러리](/docs/policy-types/cel-libraries/)에 더해 ImageValidatingPolicy 유형은 아래 라이브러리도 지원한다.

Kyverno는 이미지 서명과 증명을 검증하는 전용 함수를 제공한다.

| CEL 표현식                                                                  | 용도                                          |
| --------------------------------------------------------------------------- | --------------------------------------------- |
| `images.containers`                                                         | 리소스에 있는 모든 컨테이너 이미지를 가져온다 |
| `verifyImageSignatures(image, [attestors.notary])`                          | 지정한 attestor로 이미지 서명을 검증한다    |
| `verifyAttestationSignatures(image, attestations.sbom, [attestors.notary])` | 특정 메타데이터의 증명 서명을 검증한다      |
| `extractPayload(image, attestations.sbom).bomFormat == 'CycloneDX'`         | in-toto 페이로드를 추출한다                 |

다음 정책은 이 함수들을 사용하는 예시이다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: check-images
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['pods']
  matchImageReferences:
    - glob: ghcr.io/*
      attestors:
        - name: notary
          notary:
            certs:
              value: |-
                -----BEGIN CERTIFICATE-----
                ...
                -----END CERTIFICATE-----
      attestations:
        - name: sbom
          referrer:
            type: sbom/cyclone-dx
  validations:
    - expression: >-
        images.containers.map(image, verifyImageSignatures(image, [attestors.notary])).all(e, e > 0)
      message: failed to verify image with notary cert
    - expression: >-
        images.containers.map(image, verifyAttestationSignatures(image, 
           attestations.sbom, [attestors.notary])).all(e, e > 0)
      message: failed to verify attestation with notary cert
    - expression: >-
        images.containers.map(image, extractPayload(image, attestations.sbom).bomFormat == 'CycloneDX').all(e, e)
      message: sbom is not a cyclone dx sbom
```

이 정책은 다음을 보장한다.

1. 모든 이미지가 지정한 notary attestor로 서명되어 있다.
2. 모든 이미지에 유효한 SBOM 증명이 있다.
3. 모든 SBOM이 CycloneDX 형식이다.

:::note[참고]
`extractPayload()`가 반환하는 페이로드의 형태는 증명을 첨부한 방식에 따라 다른다. 위 정책처럼 `referrer` 증명이면 참조된 아티팩트 자체가 반환되므로 CycloneDX SBOM의 필드가 최상위에 있다. `cosign attest`로 만든 것 같은 `intoto` 증명이면 in-toto 스테이트먼트 전체가 반환되고, predicate의 필드는 `predicate` 아래에 있다. 다음은 cosign 키리스로 증명한 SBOM에 같은 검사를 적용하는 `spec` 일부이다.

```yaml
spec:
  attestors:
    - name: cosign
      cosign:
        keyless:
          identities:
            - subject: 'https://github.com/myorg/myrepo/.github/workflows/*'
              issuer: 'https://token.actions.githubusercontent.com'
        ctlog:
          url: 'https://rekor.sigstore.dev'
  attestations:
    - name: sbom
      intoto:
        type: https://cyclonedx.org/bom
  validations:
    - expression: >-
        images.containers.map(image, verifyAttestationSignatures(image, attestations.sbom, [attestors.cosign])).all(e, e > 0) &&
        images.containers.map(image, extractPayload(image, attestations.sbom).predicate.bomFormat == 'CycloneDX').all(e, e)
      message: sbom is not a signed cyclone dx sbom
```

:::

## 네임스페이스 정책

ImageValidatingPolicy에는 클러스터 범위 버전과 네임스페이스 범위 버전이 있다.

- **`ImageValidatingPolicy`**: 클러스터 범위이다. 모든 네임스페이스에 걸쳐 이미지를 검증한다.
- **`NamespacedImageValidatingPolicy`**: 네임스페이스 범위이다. 같은 네임스페이스 안의 리소스에만 이미지 검증을 적용한다.

두 정책은 기능과 필드 구조가 같고, 리소스를 선택하는 범위만 다른다.

**NamespacedImageValidatingPolicy 예시**

```yaml
apiVersion: policies.kyverno.io/v1
kind: NamespacedImageValidatingPolicy
metadata:
  name: verify-team-images
  namespace: development
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: [CREATE, UPDATE]
        resources: [pods]
  matchImageReferences:
    - glob: 'ghcr.io/myorg/dev-*'
  attestors:
    - name: devteam
      cosign:
        keyless:
          identities:
            - issuer: 'https://token.actions.githubusercontent.com'
              subject: '*@myorg.github.io'
  validations:
    - message: 'image must be signed by the development team'
      expression: >-
        images.containers.map(image, verifyImageSignatures(image, [attestors.devteam])).all(e, e > 0)
```

`NamespacedImageValidatingPolicy`를 쓰면 네임스페이스 소유자가 cluster-admin 권한 없이도 이미지 검증 정책을 직접 관리할 수 있다. 개발 팀은 CI/CD 파이프라인이 서명한 이미지인지 확인하는 식으로 자기 팀의 이미지 보안 요건을 직접 시행할 수 있고, 다른 네임스페이스에는 영향을 주지 않으며 클러스터 수준 권한도 필요하지 않는다.

## 다른 예시

### Cosign 키리스 검증

이 예시 정책은 Cosign 키리스 서명으로 컨테이너 이미지 서명을 검증하고, 취약점 스캔 증명이 있는지도 확인한다.

Kyverno는 키리스 attestor를 설정할 때 identities.subjectRegExp와 identities.issuerRegExp 필드에 정규식을 쓸 수 있다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: require-vulnerability-scan
spec:
  validationActions: [Audit]
  webhookConfiguration:
    timeoutSeconds: 15
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        resources: ['pods']
        operations: ['CREATE', 'UPDATE']
  matchImageReferences:
    - glob: 'ghcr.io/myorg/myrepo:*'
  attestors:
    - name: cosign
      cosign:
        keyless:
          identities:
            - subject: 'https://github.com/myorg/myrepo/.github/workflows/*'
              issuer: 'https://token.actions.githubusercontent.com'
        ctlog:
          url: 'https://rekor.sigstore.dev'
  attestations:
    - name: cosignAttestation
      intoto:
        type: cosign.sigstore.dev/attestation/vuln/v1
  validations:
    - expression: >-
        images.containers.map(image, verifyImageSignatures(image,  [attestors.cosign])).all(e, e > 0)
      message: 'Failed image signature verification'
    - expression: >-
        images.containers.map(image, verifyAttestationSignatures(image, attestations.cosignAttestation, [attestors.cosign])).all(e, e > 0)
      message: 'Failed to verify vulnerability scan attestation with Cosign keyless'
```

:::note[참고]
증명 이름에 `-` 같은 특수 문자가 들어 있으면 대괄호 문법으로 접근한다.

```yaml
attestations["cosign-attes"]
```

CEL 표현식에서 파싱 문제가 생기지 않도록 이름은 camelCase나 snake_case로 짓는 편이 좋다.
:::

### Cosign 키 기반 검증

이 정책은 컨테이너 이미지가 지정한 Cosign 공개 키로 서명되었는지 확인한 뒤에야 어드미션을 허용한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: verify-image-ivpol
spec:
  webhookConfiguration:
    timeoutSeconds: 15
  evaluation:
    background:
      enabled: false
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['pods']
  matchImageReferences:
    - glob: 'docker.io/kyverno/kyverno*'
  attestors:
    - name: cosign
      cosign:
        key:
          data: |
            -----BEGIN PUBLIC KEY-----
            MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE6QsNef3SKYhJVYSVj+ZfbPwJd0pv
            DLYNHXITZkhIzfE+apcxDjCCkDPcJ3A3zvhPATYOIsCxYPch7Q2JdJLsDQ==
            -----END PUBLIC KEY-----
  validations:
    - expression: >-
        images.containers.map(image, verifyImageSignatures(image, [attestors.cosign])).all(e ,e > 0)
      message: >-
        failed the image Signature verification
```

참고: Cosign 키리스 서명으로 컨테이너 이미지에 서명하는 방법은 [Cosign 공식 문서](https://docs.sigstore.dev/cosign/signing/signing_with_containers/)를 참고한다.
정책은 클러스터를 보호하려고 클러스터 전체에 적용된다. 하지만 팀이나 사용자가 특정 도구나 리소스를 테스트해야 할 때가 있다. 이럴 때는 [PolicyException](/docs/guides/exceptions#policyexceptions-for-cel-policies)을 사용하면 정책을 고치지 않고도 정책을 우회할 수 있다. 정책의 보안 수준은 유지하면서 필요할 때 우회할 여지를 줄 수 있다.

### Sigstore 신뢰 루트

프라이빗 Sigstore 환경에서는 키리스 검증이 시스템 루트 대신 사용자 정의 신뢰 루트를 쓸 수 있다. Fulcio, Rekor, CT 로그의 신뢰 자료를 조직 내부에서 관리하며 컨피그맵(ConfigMap) 등 CEL로 접근할 수 있는 곳에 저장할 때 유용하다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: verify-build-metadata
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['pods']
  matchImageReferences:
    - glob: 'ghcr.io/nirmata/demo-private-attestations*'
  variables:
    - name: githubTrustedRoot
      expression: >-
        resource.get("v1", "configmaps", "kyverno", "github-trusted-root").data["trusted_root.json"]
  attestations:
    - name: buildMeta
      intoto:
        type: 'https://nirmata.com/attestations/build-metadata/v1'
  attestors:
    - name: github
      cosign:
        keyless:
          identities:
            - issuer: 'https://token.actions.githubusercontent.com'
              subjectRegExp: '^https://github\\.com/nirmata/demo-attestations-kyverno/\\.github/workflows/reusable-build-attest\\.yml@refs/(heads/main|tags/v.*)$'
        trustedRoot:
          expression: variables.githubTrustedRoot
        ctlog:
          insecureIgnoreTlog: true
          insecureIgnoreSCT: true
  validations:
    - expression: >-
        images.containers.map(image,
          verifyAttestationSignatures(image, attestations.buildMeta, [attestors.github]) > 0
            ? extractPayload(image, attestations.buildMeta)
            : dyn(null)).all(p, p != null)
      message: 'Failed to verify build-metadata attestation'
```

`trustedRoot` 필드로 Sigstore 신뢰 루트 JSON 전체를 키리스 검증기에 전달할 수 있다. 위 예시에서는 신뢰 루트를 컨피그맵에서 읽고, CEL을 거쳐 attestor에 넘긴다.

:::note[참고]
`extractPayload()`를 쓰려면 먼저 `verifyAttestationSignatures()`로 증명을 검증해야 한다. 검증하지 않으면 오류를 반환한다.
:::

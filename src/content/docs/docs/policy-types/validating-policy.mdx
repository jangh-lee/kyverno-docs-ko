Kyverno `ValidatingPolicy`는 쿠버네티스 `ValidatingAdmissionPolicy`를 확장한 유형이다. 복잡한 정책 평가와 Policy-as-Code에 필요한 기능을 더했다. `ValidatingPolicy`는 `ValidatingAdmissionPolicy`의 상위 집합이며, Kyverno 고유 기능을 위한 필드를 추가로 갖는다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-labels
spec:
  validationActions:
    - Deny
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [pods]
  validations:
    - message: label 'environment' is required
      expression: "'environment' in object.metadata.?labels.orValue([])"
```

## ValidatingAdmissionPolicy와 비교

아래 표는 쿠버네티스 `ValidatingAdmissionPolicy`와 Kyverno `ValidatingPolicy`의 주요 기능을 비교한 것이다.

| 기능             | ValidatingAdmissionPolicy | ValidatingPolicy                            |
| ---------------- | ------------------------- | ------------------------------------------- |
| 적용 시점        | 어드미션                  | 어드미션, 백그라운드, 파이프라인 등         |
| 페이로드         | 쿠버네티스                | 쿠버네티스, 모든 JSON·YAML                  |
| 배포 방식        | 쿠버네티스                | Helm, CLI, 웹 서비스, API, SDK              |
| CEL 라이브러리   | 기본                      | 확장                                        |
| 바인딩           | 수동                      | 자동                                        |
| 자동 생성        | -                         | 파드 컨트롤러, ValidatingAdmissionPolicy    |
| 외부 데이터      | \_                        | 쿠버네티스 리소스, API 호출                 |
| 캐싱             | \_                        | 글로벌 컨텍스트, 이미지 검증 결과           |
| 백그라운드 스캔  | -                         | 주기적 실행, 정책 생성·변경 시 실행         |
| 예외             | -                         | 세분화된 예외                               |
| 리포팅           | \_                        | Policy WG Reports API                       |
| 테스트           | \_                        | Kyverno CLI(단위), Chainsaw(e2e)            |

## 추가 필드

`ValidatingPolicy`는 [쿠버네티스 ValidatingAdmissionPolicy](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)에 Kyverno 기능을 위한 필드를 더했다. 전체 레퍼런스는 [API 명세](https://htmlpreview.github.io/?https://github.com/kyverno/kyverno/blob/main/docs/user/crd/index.html#policies.kyverno.io/v1.ValidatingPolicy)에서 볼 수 있다.

### evaluation

`spec.evaluation` 필드는 정책을 어떻게 적용하고 페이로드를 어떻게 처리할지 정한다. <span class="hl-link" tabindex="0" data-code="evaluation-sample.yaml" data-lines="7-10">정책의 어드미션 요청 처리와 백그라운드 처리를 켜거나 끌 수 있고</span>, <span class="hl-link" tabindex="0" data-code="evaluation-sample.yaml" data-lines="11">페이로드를 JSON으로 처리할지 쿠버네티스 리소스로 처리할지</span>도 여기서 정한다.

```yaml title="evaluation-sample.yaml"
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: sample
spec:
  evaluation:
    admission:
      enabled: false
    background:
      enabled: true
    mode: Kubernetes
  # ...
```

Kubernetes가 아닌 페이로드에는 `mode`를 `JSON`으로 설정한다.

자세한 내용은 [API 레퍼런스](https://htmlpreview.github.io/?https://github.com/kyverno/kyverno/blob/main/docs/user/crd/index.html#policies.kyverno.io/v1.EvaluationConfiguration)를 참고한다.

### webhookConfiguration

`spec.webhookConfiguration` 필드는 Kyverno 어드미션 컨트롤러 웹훅 설정을 관리하는 속성을 정의한다.

```yaml title="webhook-timeout.yaml"
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-deployment-labels
spec:
  webhookConfiguration:
    timeoutSeconds: 15
  # ...
```

위 정책은 <span class="hl-link" tabindex="0" data-code="webhook-timeout.yaml" data-lines="6-7">`webhookConfiguration.timeoutSeconds`를 `15`로 설정했다</span>. 어드미션 요청이 정책 평가를 기다리는 시간이다. 기본값은 `10`초이고 설정 가능한 범위는 `1`~`30`초이다. 이 시간이 지나면 실패 정책(failurePolicy)에 따라 요청이 실패하거나 평가 결과가 무시될 수 있다. Kyverno는 이 설정을 생성되는 `ValidatingWebhookConfiguration`에 반영한다.

자세한 내용은 [API 레퍼런스](https://htmlpreview.github.io/?https://github.com/kyverno/kyverno/blob/main/docs/user/crd/index.html#policies.kyverno.io/v1.WebhookConfiguration)를 참고한다.

### autogen

`spec.autogen` 필드는 정책 자동 생성 동작을 정의한다. 파드 컨트롤러용 정책을 자동으로 만들거나, 쿠버네티스 API 서버에서 실행할 `ValidatingAdmissionPolicy`를 생성할 수 있다.

:::note[참고]
파드 컨트롤러 자동 생성과 `ValidatingAdmissionPolicy` 생성은 함께 쓸 수 없다. `spec.autogen.podControllers`를 설정하면 Kyverno는 `ValidatingAdmissionPolicy`를 만들지 않고, 그 이유를 정책 status에 기록한다. `ValidatingAdmissionPolicy`는 쿠버네티스 API 서버가 직접 평가하기 때문에 Kyverno가 만든 파드 컨트롤러용 규칙 변형을 담을 수 없기 때문이다.

정책을 참조하는 `PolicyException`이 [보상 통제](/docs/guides/exceptions#compensating-controls)를 정의한 경우에도 Kyverno는 `ValidatingAdmissionPolicy`를 만들지 않는다. API 서버가 보상 통제를 평가할 수 없기 때문이다.
:::

다음은 `ValidatingPolicy` 선언에서 <span class="hl-link" tabindex="0" data-code="autogen-pod-controllers.yaml" data-lines="8-12">deployments, jobs, cronjobs, statefulsets용 정책을 생성하는</span> 예시이다.

```yaml title="autogen-pod-controllers.yaml"
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: disallow-capabilities
spec:
  autogen:
    podControllers:
      controllers:
        - deployments
        - jobs
        - cronjobs
        - statefulsets
```

다음은 `ValidatingPolicy` 선언에서 <span class="hl-link" tabindex="0" data-code="autogen-vap.yaml" data-lines="6-8">`ValidatingAdmissionPolicy`를 생성하는</span> 예시이다.

```yaml title="autogen-vap.yaml"
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: disallow-capabilities
spec:
  autogen:
    validatingAdmissionPolicy:
      enabled: true
```

`ValidatingPolicy`에서 `ValidatingAdmissionPolicy`를 생성하면 Kyverno의 모든 기능을 활용하면서도 어드미션 제어를 더 빠르고 안정적으로 실행할 수 있다.

자세한 내용은 [API 레퍼런스](https://htmlpreview.github.io/?https://github.com/kyverno/kyverno/blob/main/docs/user/crd/index.html#policies.kyverno.io/v1.AutogenConfiguration)를 참고한다.

## 정책 범위

ValidatingPolicy에는 클러스터 범위 버전과 네임스페이스 범위 버전이 있다.

- **`ValidatingPolicy`**: 클러스터 범위이다. 모든 네임스페이스의 리소스에 적용된다.
- **`NamespacedValidatingPolicy`**: 네임스페이스 범위이다. 같은 네임스페이스 안의 리소스에만 적용된다.

두 정책은 기능과 필드 구조가 같고, 리소스를 선택하는 범위만 다르다.

### NamespacedValidatingPolicy 예시

```yaml title="check-deployment-replicas.yaml"
apiVersion: policies.kyverno.io/v1
kind: NamespacedValidatingPolicy
metadata:
  name: check-deployment-replicas
  namespace: production
spec:
  validationActions:
    - Deny
  matchConstraints:
    resourceRules:
      - apiGroups: ['apps']
        apiVersions: ['v1']
        operations: [CREATE, UPDATE]
        resources: ['deployments']
  validations:
    - message: 'deployments must have at least 2 replicas for high availability'
      expression: 'object.spec.replicas >= 2'
```

`NamespacedValidatingPolicy`를 쓰면 <span class="hl-link" tabindex="0" data-code="check-deployment-replicas.yaml" data-lines="2,5">네임스페이스 소유자가 cluster-admin 권한 없이도 검증 정책을 직접 관리할 수 있다</span>. 멀티 테넌시와 보안 격리 면에서 이점이 있다.

## Kyverno CEL 라이브러리

Kyverno는 Kubernetes의 CEL 환경에 라이브러리를 더해 복잡한 정책 로직과 고급 기능을 쓸 수 있게 한다. 사용할 수 있는 CEL 라이브러리 전체는 [CEL 라이브러리 문서](/docs/policy-types/cel-libraries/)를 참고한다.

## 예외

정책은 기본적으로 클러스터 전체에 적용된다. 하지만 예외가 필요할 때가 있다. 이럴 때는 [PolicyException](/docs/guides/exceptions#policyexceptions-for-cel-policies)을 사용해 정책을 고치지 않고도 일부 리소스가 정책을 우회하도록 허용할 수 있다. 정책의 보안 수준은 그대로 두고 필요할 때 예외를 줄 수 있다. 예외에는 [보상 통제](/docs/guides/exceptions#compensating-controls)도 정의할 수 있으며, 리소스가 이를 충족해야 예외가 인정된다.

## JSON 페이로드

Kyverno ValidatingPolicy는 어떤 JSON 페이로드에도 적용할 수 있다. 다음은 Terraform 플랜에 적용해 EKS 클러스터가 퍼블릭 엔드포인트를 노출하지 않는지 확인하는 정책 예시이다.

```yaml title="check-public-endpoint.yaml"
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-public-endpoint
spec:
  evaluation:
    mode: JSON
  matchConditions:
    - name: is-terraform-plan
      expression: 'has(object.planned_values) && has(object.terraform_version)'
    - name: has-eks-cluster
      expression: |
        has(object.planned_values) && 
          (has(object.planned_values.root_module) && has(object.planned_values.root_module.child_modules) &&
           object.planned_values.root_module.child_modules.exists(m, 
             has(m.resources) && m.resources.exists(r, r.type == 'aws_eks_cluster')))
  validations:
    - message: 'Public access to EKS cluster endpoint must be set to false'
      expression: |
        (
          (!has(object.planned_values.root_module.child_modules) ||
           object.planned_values.root_module.child_modules.all(module,
             !has(module.resources) ||
             module.resources.filter(r, r.type == 'aws_eks_cluster').all(cluster,
               !has(cluster.values.vpc_config) ||
               cluster.values.vpc_config.all(vpc,
                 !has(vpc.endpoint_public_access) || vpc.endpoint_public_access == false
               )
             )
           ))
        )
```

JSON 페이로드용 정책은 다음 순서로 작성한다.

1. <span class="hl-link" tabindex="0" data-code="check-public-endpoint.yaml" data-lines="6-7">`spec.evaluation.mode`를 `JSON`으로 설정한다</span>.
2. <span class="hl-link" tabindex="0" data-code="check-public-endpoint.yaml" data-lines="8-16">`spec.matchConditions`에 CEL 표현식을 정의해 어떤 페이로드를 매칭할지 엔진에 알려 준다</span>.
3. <span class="hl-link" tabindex="0" data-code="check-public-endpoint.yaml" data-lines="17-31">검증 규칙을 `spec.validations`에 정의한다</span>.

JSON 정책은 [Kyverno CLI](/docs/subprojects/kyverno-cli)로 평가한다.

Kyverno Engine SDK는 이후 릴리스에서 제공할 예정이다.

## ValidatingPolicy의 리포트 상세 정보

ValidatingPolicy를 평가하면 결과가 PolicyReport에 기록된다. PolicyReport는 정책 평가 결과를 요약하는 표준 쿠버네티스 사용자 정의 리소스로, 리소스가 검증을 통과했는지 실패했는지 보여 준다.

Kyverno는 ValidatingPolicy 규칙에 필드를 추가로 제공해 PolicyReport가 더 많은 맥락을 담도록 한다. 중요한 기능은 두 가지이다.

### auditAnnotations로 사용자 정의 데이터 추가

auditAnnotations 필드를 쓰면 PolicyReport에 저장되는 결과에 <span class="hl-link" tabindex="0" data-code="audit-annotations.yaml" data-lines="6-8">사용자 정의 키-값 데이터를 붙일 수 있다</span>. 값은 고정 문자열이어도 되고, [CEL(Common Expression Language)](/docs/policy-types/cel-libraries/)로 계산하는 동적 표현식이어도 된다.

심각도, 담당 팀, 리소스별 값 같은 메타데이터를 넣어 두면 PolicyReport를 읽는 쪽이 위반 사항을 이해하고 조치하기 쉬워진다.

**정책 예시:**

```yaml title="audit-annotations.yaml"
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-deployment-labels
spec:
  auditAnnotations:
    - key: team
      valueExpression: "'platform'"
  matchConstraints:
    resourceRules:
      - apiGroups: [apps]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [deployments]
  variables:
    - name: environment
      expression: >-
        has(object.metadata.labels) && 'env' in object.metadata.labels && object.metadata.labels['env'] == 'prod'
  validations:
    - expression: >-
        variables.environment == true
      message: >-
        Deployment labels must be env=prod
```

### messageExpression으로 동적 메시지 생성

<span class="hl-link" tabindex="0" data-code="message-expression.yaml" data-lines="23">message 필드는 고정된 실패 메시지를 제공한다</span>. <span class="hl-link" tabindex="0" data-code="message-expression.yaml" data-lines="21-22">messageExpression을 쓰면 CEL 표현식으로 메시지를 동적으로 만들 수 있어서</span>, 실패 원인을 더 구체적으로 설명할 수 있다.

message와 messageExpression을 둘 다 정의하면 messageExpression이 우선한다.

표현식은 문자열로 평가되어야 한다.

표현식이 실패하거나 잘못된 문자열(빈 문자열, 공백뿐인 문자열, 여러 줄 문자열)을 만들면 Kyverno는 고정 message를 사용한다.

**정책 예시:**

```yaml title="message-expression.yaml"
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: check-deployment-labels
  annotations:
    policies.kyverno.io/title: Check Deployment Labels
    policies.kyverno.io/category: Other
    policies.kyverno.io/severity: medium
spec:
  validationActions:
    - Audit
  matchConstraints:
    resourceRules:
      - apiGroups: [apps]
        apiVersions: [v1]
        operations: [CREATE, UPDATE]
        resources: [deployments]
  validations:
    - expression: >-
        'environment' in object.metadata.labels
      messageExpression: >-
        "Deployment " + object.metadata.name + " is missing required label 'environment'"
      message: Deployment is missing required label
```

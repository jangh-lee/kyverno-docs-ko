GeneratingPolicy는 CEL(Common Expression Language) 표현식으로 쿠버네티스 리소스를 만들고 복제한다. CEL을 중심에 둔 방식이라 쿠버네티스 정책 표준에 맞춰 유연하게 리소스를 생성할 수 있다.

GeneratingPolicy는 CEL을 사용하므로 ValidatingAdmissionPolicy, MutatingAdmissionPolicy 같은 쿠버네티스 기본 구성 요소와 일관된 방식으로 쓸 수 있다.

주요 이점은 다음과 같다.

- **선언적 생성:** 간결한 CEL 표현식을 정책 안에 직접 써서 리소스를 정의하고 관리한다.

- **강력한 복제:** CEL 기반 접근자로 시크릿(Secret), 컨피그맵(ConfigMap) 같은 기존 리소스를 네임스페이스 사이에서 쉽게 복제한다.

- **안정적인 동기화:** 정책, 트리거, 소스 리소스가 바뀌면 생성된 리소스도 맞춰 갱신한다.

- **반복 처리:** forEach 반복문과 같은 동작으로 목록을 기준으로 리소스를 생성한다.

- **쿠버네티스 네이티브 방식:** 익숙한 CEL 기반 방식이라 쿠버네티스 생태계와 자연스럽게 어우러진다.

예를 들어 다음 정책은 default 네임스페이스의 이미지 풀 시크릿을 새로 만든 모든 네임스페이스(Namespace)에 자동으로 복제한다.

```yaml title="clone-image-pull-secret.yaml"
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: clone-image-pull-secret
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['namespaces']
  variables:
    - name: targetNs
      expression: 'object.metadata.name'
    - name: sourceSecret
      expression: resource.Get("v1", "secrets", "default", "regcred")
  generate:
    - expression: generator.Apply(variables.targetNs, [variables.sourceSecret])
```

이 정책에서는 <span class="hl-link" tabindex="0" data-code="clone-image-pull-secret.yaml" data-lines="6-11">새 네임스페이스가 만들어지면(**트리거**)</span> Kyverno가 <span class="hl-link" tabindex="0" data-code="clone-image-pull-secret.yaml" data-lines="15-16">default 네임스페이스에서 `regcred` 시크릿(**소스**)을 가져와</span> <span class="hl-link" tabindex="0" data-code="clone-image-pull-secret.yaml" data-lines="17-18">새 네임스페이스에 복사본(**다운스트림** 리소스)을 만든다</span>.

## 핵심 개념

GeneratingPolicy를 쓰려면 다음 용어를 알아야 한다.

| 용어           | 설명                                                                                          |
| :------------- | :-------------------------------------------------------------------------------------------- |
| **트리거**     | 생성 과정을 시작하는 리소스이다. 정책의 `matchConstraints`로 정의한다.                    |
| **다운스트림** | 트리거 이벤트의 결과로 정책이 생성한 리소스이다.                                            |
| **소스**       | 복제할 때 템플릿으로 쓰는 기존 리소스이다. `resource.Get`이나 `resource.List`로 가져온다. |

GeneratingPolicy의 spec은 여러 주요 필드로 이루어진다.

| 필드               | 설명                                                                                                                    |
| :----------------- | :---------------------------------------------------------------------------------------------------------------------- |
| `evaluation`       | 정책의 런타임 동작을 설정한다. `synchronize`, `generateExisting`, `orphanDownstreamOnPolicyDelete`가 여기에 속한다. |
| `matchConstraints` | **트리거** 리소스를 정의한다. 이 규칙에 맞는 리소스가 생성되거나 수정되면 정책이 동작한다.                          |
| `matchConditions`  | 트리거 리소스를 한 번 더 걸러내는 CEL 표현식이다(선택). 이 조건을 만족해야만 정책이 실행된다.                       |
| `variables`        | 정책 전체에서 재사용할 수 있는 이름 붙은 CEL 표현식 목록이다. 복잡한 로직을 단순하게 만들어 준다.                   |
| `generate`         | 생성 로직을 실행하는 CEL 표현식 목록이다. 보통 `generator.Apply()` 함수를 사용한다.                                 |

## 데이터 소스

데이터 소스 모드에서는 다운스트림 리소스를 CEL 표현식으로 정책 안에 직접 정의한다.

**사용 시점:** 트리거(예: 새 네임스페이스)에 반응해 기본 네트워크폴리시(NetworkPolicy), 롤바인딩(RoleBinding), 설정용 컨피그맵처럼 내용이 고정되었거나 템플릿으로 만들 수 있는 리소스를 생성할 때 알맞다.

다음 정책은 네임스페이스가 생성되면 컨피그맵을 생성한다.

```yaml title="zk-kafka-address-data.yaml"
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: zk-kafka-address
spec:
  evaluation:
    synchronize:
      enabled: true
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['namespaces']
  variables:
    - name: nsName
      expression: 'object.metadata.name'
    - name: downstream
      expression: >-
        [
          {
            "kind": dyn("ConfigMap"),
            "apiVersion": dyn("v1"),
            "metadata": dyn({
              "name": "zk-kafka-address",
              "namespace": string(variables.nsName),
            }),
            "data": dyn({
              "KAFKA_ADDRESS": "192.168.10.13:9092,192.168.10.14:9092,192.168.10.15:9092",
              "ZK_ADDRESS": "192.168.10.10:2181,192.168.10.11:2181,192.168.10.12:2181"
            })
          }
        ]
  generate:
    - expression: generator.Apply(variables.nsName, variables.downstream)
```

이 정책은 네임스페이스가 생성될 때마다 동작한다. <span class="hl-link" tabindex="0" data-code="zk-kafka-address-data.yaml" data-lines="16-33">네임스페이스 이름을 `nsName`에 담고, 컨피그맵 오브젝트 전체를 `downstream`에 정의한다</span>. 그다음 <span class="hl-link" tabindex="0" data-code="zk-kafka-address-data.yaml" data-lines="34-35">`generator.Apply()` 함수가 `downstream`에 정의한 컨피그맵을 대상 네임스페이스에 만든다</span>.

## YAML 템플릿

<FeatureState state="beta" version="v1.19" />

YAML 템플릿은 다운스트림 리소스를 YAML 중심으로 선언하는 또 다른 방법이다. 중첩된 CEL 표현식과 `dyn()` 호출로 오브젝트를 구성하는 대신, 생성할 리소스를 일반 YAML로 작성하고 필요하면 CEL 플레이스홀더를 끼워 넣는다. 이 내용은 `generate` 항목에 바로 쓴다.

**사용 시점:** 다운스트림 리소스가 매니페스트 형태에 가까워서(네트워크폴리시, 롤바인딩, LimitRange, 중첩이 깊은 사용자 정의 리소스 등) YAML로 선언하는 편이 가장 쉬울 때 알맞다.

`generate[]`의 각 항목에는 `expression`과 `template` 중 정확히 하나만 쓸 수 있다. 한 정책 안에서 두 종류를 섞어 쓸 수는 있다.

| 필드                   | 설명                                                                                                                              |
| :--------------------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| `template.value`       | 다운스트림 리소스를 각각 설명하는 문서를 하나 이상 담은 YAML 문자열이다. 문서는 `---`로 구분한다.                             |
| `template.interpolate` | 플레이스홀더 평가 방식을 정한다. `none`(기본값)은 값을 일반 YAML로 취급하고, `cel`은 `(( ... ))` 플레이스홀더를 CEL로 평가한다. |

다음 정책은 위의 데이터 소스 예시와 같은 일을 YAML 템플릿으로 작성한 것이다.

```yaml title="zk-kafka-address-template.yaml"
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: zk-kafka-address
spec:
  evaluation:
    synchronize:
      enabled: true
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['namespaces']
  variables:
    - name: nsName
      expression: 'object.metadata.name'
  generate:
    - template:
        interpolate: cel
        value: |
          apiVersion: v1
          kind: ConfigMap
          metadata:
            name: zk-kafka-address
            namespace: (( variables.nsName ))
          data:
            KAFKA_ADDRESS: 192.168.10.13:9092,192.168.10.14:9092,192.168.10.15:9092
            ZK_ADDRESS: 192.168.10.10:2181,192.168.10.11:2181,192.168.10.12:2181
```

렌더링된 문서는 `generator.Apply()`와 같은 생성 런타임을 거친다. 그래서 동기화, 기존 리소스의 생성, 고아(orphan) 처리 동작, 네임스페이스 범위 강제가 표현식 모드와 똑같이 동작한다.

### 플레이스홀더 동작 방식

플레이스홀더는 생성 표현식과 같은 컨텍스트(`object`, `variables`, [CEL 라이브러리](/docs/policy-types/cel-libraries))에서 평가된다. 보간은 텍스트 치환이 아니라 구조 단위로 이루어진다.

- <span class="hl-link" tabindex="0" data-code="placeholder-types.yaml" data-lines="15">값 **전체**를 차지하는 플레이스홀더는 그대로 끼워 넣어지며</span>, 맵과 리스트를 포함한 어떤 CEL 타입으로도 평가될 수 있다. `dyn()` 변환은 필요 없다.
- <span class="hl-link" tabindex="0" data-code="placeholder-types.yaml" data-lines="12,19">**더 긴 문자열 안에 들어 있는** 플레이스홀더는 문자열로 보간되므로</span> 스칼라(문자열, 숫자, 불리언)로 평가되어야 한다.

```yaml title="placeholder-types.yaml"
variables:
  - name: selector
    expression: >-
      {"matchLabels": {"kubernetes.io/metadata.name": object.metadata.name}}
generate:
  - template:
      interpolate: cel
      value: |
        apiVersion: cilium.io/v2
        kind: CiliumNetworkPolicy
        metadata:
          name: (( object.metadata.name ))-scraping   # 문자열에 포함: 문자열 보간
          namespace: (( object.metadata.name ))
        spec:
          endpointSelector: (( variables.selector ))  # 값 전체: 맵 전체를 끼워 넣음
          ingress:
          - toPorts:
            - ports:
              - port: (( string(variables.port) ))    # 평가됨
                protocol: TCP                         # 정적 값, 그대로 유지
```

정적 내용과 보간 내용은 같은 매핑이나 리스트 안에서 자유롭게 섞을 수 있다. 평가하는 대상은 플레이스홀더 노드뿐이고 나머지는 그대로 통과한다.

::::note[참고]
매핑 키에는 플레이스홀더를 쓸 수 없다. 동적 키가 필요하면 상위 필드에 값 전체 플레이스홀더를 쓴다. 예: `labels: (( variables.labels ))`
::::

보간 템플릿에 `((`를 문자 그대로 넣으려면 `\((`로 이스케이프한다. `interpolate: none`(기본값)이면 플레이스홀더를 평가하지 않고 값을 일반 YAML로 파싱한다.

### 여러 리소스 생성

템플릿 하나에 YAML 문서를 여러 개 넣을 수 있다. 각 문서는 독립적으로 생성되며, 문서 안의 `metadata.namespace`가 대상 네임스페이스가 된다.

```yaml
generate:
  - template:
      interpolate: cel
      value: |
        apiVersion: v1
        kind: ConfigMap
        metadata:
          name: (( variables.nsName ))-config
          namespace: (( variables.nsName ))
        data:
          key: value
        ---
        apiVersion: v1
        kind: Secret
        metadata:
          name: (( variables.nsName ))-secret
          namespace: (( variables.nsName ))
        type: Opaque
        stringData:
          password: change-me
```

### 네임스페이스 지정

생성되는 각 리소스의 대상 네임스페이스는 렌더링된 `metadata.namespace`에서 가져온다. 네임스페이스가 없는 리소스는 클러스터 범위로 취급한다. NamespacedGeneratingPolicy에서는 네임스페이스가 없는 문서가 정책 자신의 네임스페이스를 기본값으로 쓰고, 그 외 네임스페이스는 거부된다.

::::note[참고]
런타임에 계산한 네임스페이스 집합에 같은 리소스를 생성하는 팬아웃(fan-out)은 템플릿으로 표현할 수 없다. 이 패턴에는 표현식 모드에서 CEL 반복문 안에 `generator.Apply()`를 쓴다. [반복 처리](#반복-처리)를 참고한다.
::::

## 복제 소스

이 모드는 기존 쿠버네티스 리소스(소스)를 복사해 새 리소스(다운스트림)를 만든다. `resource.Get()`이나 `resource.List()`로 소스 리소스를 가져오고, `generator.Apply()`로 대상 네임스페이스에 복제한다.

**사용 시점:** 이미지 풀 시크릿(regcred), TLS 인증서, 표준 네트워크폴리시 같은 공통 리소스를 중앙 네임스페이스에서 다른 네임스페이스로 배포할 때 알맞다.

### 리소스 하나 복제

리소스 하나를 복제하려면 `resource.Get()`으로 소스 리소스를 가져온 다음 대상 네임스페이스에 적용한다.

다음은 `default` 네임스페이스의 시크릿을 대상 네임스페이스로 복제하는 예시이다.

```yaml title="generate-secret.yaml"
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: generate-secret
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['namespaces']
  variables:
    - name: nsName
      expression: 'object.metadata.name'
    - name: source
      expression: resource.Get("v1", "secrets", "default", "regcred")
  generate:
    - expression: generator.Apply(variables.nsName, [variables.source])
```

이 정책은 네임스페이스가 생성될 때마다 동작한다. <span class="hl-link" tabindex="0" data-code="generate-secret.yaml" data-lines="13-16">트리거의 네임스페이스 이름을 `nsName`에 담고, `resource.Get()`으로 `default` 네임스페이스의 `regcred` 시크릿을 가져와 `source`에 저장한다</span>. 그다음 <span class="hl-link" tabindex="0" data-code="generate-secret.yaml" data-lines="17-18">`generator.Apply()`가 가져온 시크릿을 새 네임스페이스에 복사한다</span>.

### 여러 리소스 복제

여러 리소스를 복제하려면 `resource.List()`로 리소스 목록을 가져와 대상 네임스페이스에 적용한다. 다음은 `default` 네임스페이스의 모든 시크릿을 복제하는 예시이다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: generate-secrets
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['namespaces']
  variables:
    - name: nsName
      expression: 'object.metadata.name'
    - name: sources
      expression: resource.List("v1", "secrets", "default")
  generate:
    - expression: generator.Apply(variables.nsName, [variables.sources])
```

이 정책은 네임스페이스가 생성될 때마다 동작한다. 트리거의 네임스페이스 이름을 `nsName`에 담고, `resource.List()`로 `default` 네임스페이스의 모든 시크릿을 가져와 `sources`에 저장한다. 그다음 `generator.Apply()`가 가져온 시크릿 전체를 새 네임스페이스에 복사한다.

## 반복 처리

GeneratingPolicy는 CEL의 리스트 처리 기능으로 forEach 방식의 로직을 지원한다. 동적인 목록을 바탕으로 리소스를 여러 개 생성할 때 유용하다.

**사용 시점:** 중앙 설정에 정의한 네임스페이스 목록 전체에 리소스를 생성하거나, 목록의 항목에 따라 서로 다른 리소스를 여러 개 만들어야 할 때 사용한다.

### 데이터 소스와 함께 반복하기

다음 정책은 컨피그맵에 쉼표로 구분한 문자열로 저장된 기존 네임스페이스 목록 전체에 네트워크폴리시를 만든다.

```yaml title="generate-np-foreach.yaml"
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: generate-network-policy
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['configmaps']
  variables:
    - name: nsList
      expression: "object.data.namespaces.split(',')"
    - name: downstream
      expression: >-
        [
          {
            "kind": dyn("NetworkPolicy"),
            "apiVersion": dyn("networking.k8s.io/v1"),
            "metadata": dyn({
              "name": "test-network-policy",
            }),
            "spec": dyn({
              "podSelector": dyn({}),
              "policyTypes": dyn(["Ingress", "Egress"])
            })
          }
        ]
  generate:
    - expression: >
        variables.nsList.all(ns, generator.Apply(ns, variables.downstream))
```

이 정책은 컨피그맵이 생성될 때마다 동작한다. <span class="hl-link" tabindex="0" data-code="generate-np-foreach.yaml" data-lines="13-29">컨피그맵의 data 필드에서 네임스페이스 목록을 읽어 리스트로 나눈 뒤 `nsList`에 저장하고, 네트워크폴리시 오브젝트 전체를 `downstream`에 정의한다</span>. 이어서 <span class="hl-link" tabindex="0" data-code="generate-np-foreach.yaml" data-lines="30-32">`variables.nsList.all(ns, ...)`로 `nsList`의 네임스페이스를 하나씩 순회하면서 `downstream`에 정의한 네트워크폴리시를 각 네임스페이스에 생성한다</span>.

반복하면서 이름이 서로 다른 리소스를 만들어야 할 때도 있다. 인덱스 목록을 만들면 인덱스로 동적인 이름을 구성하고 원래 목록의 항목을 참조할 수 있다.

다음 정책은 컨피그맵에 정의된 각 네임스페이스에 이름이 서로 다른 네트워크폴리시(예: np-0, np-1)를 만든다.

```yaml title="generate-np-indexed.yaml"
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: generate-network-policy
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['configmaps']
  variables:
    # nsList는 ["ns1", "ns2", "ns3"]이 된다
    - name: nsList
      expression: "object.data.namespaces.split(',')"
    # indexed는 [0, 1, 2]가 된다
    - name: indexed
      expression: >
        variables.nsList.map(ns, variables.nsList.indexOf(ns))
  generate:
    - expression: >
        variables.indexed.all(i, generator.Apply(variables.nsList[i], [
          {
            "kind": dyn("NetworkPolicy"),
            "apiVersion": dyn("networking.k8s.io/v1"),
            "metadata": dyn({
              "name": "np-" + string(i),
            }),
            "spec": dyn({
              "podSelector": dyn({}),
              "policyTypes": dyn(["Ingress", "Egress"])
            })
          }]
        ))
```

이 정책은 변수 두 개를 정의한다.

1. `nsList`: <span class="hl-link" tabindex="0" data-code="generate-np-indexed.yaml" data-lines="13-15">트리거 컨피그맵의 namespaces 키를 읽어 쉼표로 구분된 문자열을 이름 목록(예: ['ns1', 'ns2', 'ns3'])으로 나눈다</span>.

2. `indexed`: <span class="hl-link" tabindex="0" data-code="generate-np-indexed.yaml" data-lines="16-19">nsList 각 항목의 숫자 인덱스를 담은 새 리스트를 만든다</span>. `nsList`가 ['ns1', 'ns2', 'ns3']이면 indexed는 [0, 1, 2]가 된다. 이렇게 하면 네임스페이스마다 겹치지 않는 고정된 번호를 얻는다.

이어서 `generate` 블록이 하는 일은 다음과 같다.

1. `variables.indexed.all(i, ...):` 이 CEL 표현식은 indexed 리스트의 숫자 `i`를 하나씩 순회한다. 반복 변수 `i`에는 현재 인덱스(0, 1, 2 순서)가 들어 있다.

2. `generator.Apply(variables.nsList[i], ...):` 반복문 안에서 이 함수가 리소스를 생성한다.
   - `variables.nsList[i]`로 대상 네임스페이스를 가져온다(`i`가 1이면 `ns2`).
   - 인덱스 `i`를 이어 붙여 네트워크폴리시 이름을 동적으로 만든다(`"np-" + string(1)`의 결과는 `np-1`).

이 방식으로 컨피그맵에 정의된 네임스페이스마다 이름이 서로 다른 리소스를 생성할 수 있으므로, 각 네트워크폴리시가 구분되고 대상 네임스페이스와도 정확히 연결된다.

리소스를 생성하기 전에 목록을 필터링해야 하는 경우도 있다.

다음 정책은 필터링과 인덱싱을 함께 써서, 미리 승인된 특정 네임스페이스에만 리소스를 생성하면서 이름은 원래 인덱스를 그대로 유지한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: generate-network-policy
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['configmaps']
  variables:
    # nsList는 ["filtered-ns-1", "filtered-ns-2", "filtered-ns-3"]이다
    - name: nsList
      expression: "object.data.namespaces.split(',')"
    # filteredList는 ["filtered-ns-1", "filtered-ns-3"]이다
    - name: filteredList
      expression: "variables.nsList.filter(ns, ['filtered-ns-1', 'filtered-ns-3'].exists(v, v == ns))"
    # indexed는 [0, 2]이다
    - name: indexed
      expression: >
        variables.filteredList.map(ns, variables.nsList.indexOf(ns))
  generate:
    - expression: >
        variables.indexed.all(i, generator.Apply(variables.nsList[i], [
          {
            "kind": dyn("NetworkPolicy"),
            "apiVersion": dyn("networking.k8s.io/v1"),
            "metadata": dyn({
              "name": "filtered-np-" + string(i),
            }),
            "spec": dyn({
              "podSelector": dyn({}),
              "policyTypes": dyn(["Ingress", "Egress"])
            })
          }]
        ))
```

이 정책은 변수 세 개를 정의한다.

1. `nsList:` 트리거 컨피그맵의 namespaces 키를 읽어 전체 소스 목록으로 나눈다. 예: ['filtered-ns-1', 'filtered-ns-2', 'filtered-ns-3'].

2. `filteredList:` 핵심 단계이다. `filter()`로 `nsList` 중 하드코딩된 허용 목록 `(['filtered-ns-1', 'filtered-ns-3'])`에도 들어 있는 네임스페이스만 모은 새 리스트를 만든다. 결과는 `['filtered-ns-1', 'filtered-ns-3']`이다.

3. `indexed:` `filteredList`를 순회하되, 각 항목이 필터링 전 `nsList`에서 차지하던 원래 인덱스를 찾는다. 결과는 허용된 항목의 원래 인덱스 목록인 `[0, 2]`이다.

이어서 `generate` 블록은 이 변수들로 필터링된 네임스페이스에 네트워크폴리시를 만든다.

1. `variables.indexed.all(i, ...):` 반복문이 indexed 리스트를 순회하므로 `i`는 0, 그다음 2이다.

2. `generator.Apply(variables.nsList[i], ...):` 반복문 안에서 인덱스 `i`로 원래 목록의 올바른 네임스페이스를 고르고, 이름이 겹치지 않는 리소스를 만든다.
   - `i`가 0이면 네임스페이스 `filtered-ns-1`에 `filtered-np-0`을 만든다.
   - `i`가 2이면 네임스페이스 `filtered-ns-3`에 `filtered-np-2`를 만든다.
   - `filtered-ns-2`는 `filteredList`에 없으므로 건너뛴다.

이 방식으로 특정 네임스페이스에만 리소스를 생성하면서, 필터링 전 목록의 원래 인덱스에 따른 일관된 이름 체계를 유지할 수 있다.

### 복제 소스와 함께 반복하기

리소스를 복제할 때도 반복문으로 목록의 항목마다 리소스를 생성할 수 있다. 목록의 항목마다 리소스를 복제하고 싶을 때 특히 유용하다.

다음 정책은 컨피그맵에 정의된 각 네임스페이스에 시크릿을 복제한다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: generate-secrets
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['configmaps']
  variables:
    - name: nsList
      expression: "object.data.namespaces.split(',')"
    - name: source
      expression: resource.Get("v1", "secrets", "default", "regcred")
  generate:
    - expression: >
        variables.nsList.all(ns, generator.Apply(ns, [variables.source]))
```

이 정책은 컨피그맵이 생성될 때마다 동작한다. 컨피그맵의 data 필드에서 네임스페이스 목록을 읽어 리스트로 나눈 뒤 `nsList`에 저장하고, `default` 네임스페이스의 `regcred` 시크릿을 가져와 `source`에 저장한다. 그다음 `generate` 블록이 `variables.nsList.all(ns, ...)`로 `nsList`의 네임스페이스를 하나씩 순회하면서 각 네임스페이스에 `regcred` 시크릿 복사본을 만든다.

목록의 항목마다 리소스 여러 개를 복제할 수도 있다. 다음은 `default` 네임스페이스의 모든 시크릿을 컨피그맵에 정의된 각 네임스페이스로 복제하는 예시이다.

```yaml
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: foreach-clone-list-sync-create
spec:
  evaluation:
    synchronize:
      enabled: true
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['configmaps']
  variables:
    - name: nsList
      expression: "object.data.namespaces.split(',')"
    - name: sources
      expression: resource.List("v1", "secrets", "default")
  generate:
    - expression: >
        variables.nsList.all(ns, generator.Apply(ns, [variables.sources]))
```

이 정책은 컨피그맵이 생성될 때마다 동작한다. 컨피그맵의 data 필드에서 네임스페이스 목록을 읽어 리스트로 나눈 뒤 `nsList`에 저장하고, `default` 네임스페이스의 모든 시크릿을 가져와 `sources`에 저장한다. 그다음 `generate` 블록이 `variables.nsList.all(ns, ...)`로 `nsList`의 네임스페이스를 하나씩 순회하면서 각 네임스페이스에 가져온 시크릿 전체의 복사본을 만든다.

## 동기화

동기화는 다운스트림 리소스가 소스와 일관되게 유지되도록 한다. 소스는 정책 자체(데이터 소스)일 수도 있고 복제 대상 리소스(복제 소스)일 수도 있다. 동기화를 켜면 Kyverno가 변경 사항을 감시하다가 필요에 따라 다운스트림 리소스를 자동으로 수정하거나 삭제한다.

`evaluation.synchronize.enabled: true` 필드로 설정한다.

### 데이터 소스와 동기화

데이터 소스에 동기화를 켜면 다운스트림 리소스의 수명 주기가 정책과 트리거에 묶인다. 예를 들어 정책을 수정하면 생성된 리소스도 갱신되고, 트리거를 삭제하면 생성된 리소스도 삭제된다.

다음 표는 데이터 소스를 선언한 GeneratingPolicy의 구성 요소에 삭제나 수정 이벤트가 발생했을 때의 동작이다.

| 동작               | 동기화 사용 시                                                                     | 동기화 미사용 시      |
| ------------------ | ---------------------------------------------------------------------------------- | --------------------- |
| 다운스트림 삭제    | 다운스트림 재생성                                                                  | 다운스트림 삭제       |
| 규칙/정책 삭제     | 다운스트림 유지 <br/>`orphanDownstreamOnPolicyDelete.enabled: true`일 때           | 다운스트림 유지       |
| 규칙/정책 삭제     | 다운스트림 삭제 <br/>`orphanDownstreamOnPolicyDelete.enabled: false`일 때          | 다운스트림 유지       |
| 트리거 삭제        | 다운스트림 삭제                                                                    | 없음                  |
| 다운스트림 수정    | 다운스트림 원복                                                                    | 다운스트림 수정됨     |
| 규칙/정책 수정     | 다운스트림 동기화                                                                  | 다운스트림 그대로     |
| 트리거 수정        | 다운스트림 삭제                                                                    | 없음                  |

동기화를 켠 상태에서 정책을 삭제해도 생성된 리소스를 남기려면 `evaluation.orphanDownstreamOnPolicyDelete` 속성을 사용한다. 기본값은 false이다. true로 설정하면 리소스를 만든 정책을 삭제한 뒤에도 생성된 리소스가 클러스터에 남는다(고아 상태).

### 복제 소스와 동기화

복제 소스 모드에서 동기화는 다운스트림 복사본을 원본 소스 리소스와 맞춰 준다. 소스 리소스를 수정하거나 삭제하면 모든 다운스트림 복제본도 그에 따라 수정되거나 삭제된다.

다음 표는 복제 소스를 쓰는 GeneratingPolicy의 구성 요소에 이벤트가 발생했을 때의 동작이다. 다운스트림 리소스의 수명 주기는 주로 소스에 묶여 있으므로 정책을 삭제해도 다운스트림 리소스는 삭제되지 않는다.

| 동작               | 동기화 사용 시      | 동기화 미사용 시    |
| ------------------ | ------------------- | ------------------- |
| 다운스트림 삭제    | 다운스트림 재생성   | 다운스트림 삭제     |
| 규칙/정책 삭제     | 다운스트림 유지     | 다운스트림 유지     |
| 소스 삭제          | 다운스트림 삭제     | 다운스트림 유지     |
| 트리거 삭제        | 다운스트림 삭제     | 없음                |
| 다운스트림 수정    | 다운스트림 원복     | 다운스트림 수정됨   |
| 규칙/정책 수정     | 다운스트림 그대로   | 다운스트림 그대로   |
| 소스 수정          | 다운스트림 동기화   | 다운스트림 그대로   |
| 트리거 수정        | 다운스트림 삭제     | 없음                |

## 정책 범위

GeneratingPolicy에는 클러스터 범위 버전과 네임스페이스 범위 버전이 있다.

- **`GeneratingPolicy`**: 클러스터 범위이다. 모든 네임스페이스의 리소스에 적용된다.
- **`NamespacedGeneratingPolicy`**: 네임스페이스 범위이다. 같은 네임스페이스 안의 리소스에만 적용된다.

두 정책은 기능과 필드 구조가 같고, 리소스를 선택하는 범위만 다르다.

### NamespacedGeneratingPolicy 예시

```yaml
apiVersion: policies.kyverno.io/v1
kind: NamespacedGeneratingPolicy
metadata:
  name: clone-secret
  namespace: production
spec:
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE']
        resources: ['pods']
  variables:
    - name: nsName
      expression: 'object.metadata.namespace'
    - name: source
      expression: resource.Get("v1", "secrets", "production", "regcred")
  generate:
    - expression: generator.Apply(variables.nsName, [variables.source])
```

`NamespacedGeneratingPolicy`를 쓰면 네임스페이스 소유자가 cluster-admin 권한 없이도 생성 정책을 직접 관리할 수 있다. 멀티 테넌시와 보안 격리 면에서 이점이 있다.

## 기존 리소스에 대한 생성

GeneratingPolicy는 기본적으로 규칙에 맞는 리소스의 `CREATE`, `UPDATE`, `DELETE` 이벤트에서만 동작한다. 따라서 조건에 맞는 리소스(예: 기존 네임스페이스)가 이미 있는 클러스터에 정책을 적용해도 그 리소스에는 정책이 실행되지 않는다.

이럴 때는 `evaluation.generateExisting.enabled`를 true로 설정한다. 정책을 만들 때 트리거 규칙에 맞는 기존 리소스를 한 번 스캔해서 생성 로직을 적용한다.

**사용 시점:** 표준 시크릿이나 네트워크폴리시를 기존 네임스페이스 전체에 배포하는 것처럼, 클러스터에 이미 있는 리소스에 GeneratingPolicy를 소급 적용해야 할 때 사용한다.

다음 정책은 새 네임스페이스**와** 기존 네임스페이스 모두에 시크릿을 복제한다.

```yaml title="generate-secrets-existing.yaml"
apiVersion: policies.kyverno.io/v1
kind: GeneratingPolicy
metadata:
  name: generate-secrets
spec:
  evaluation:
    generateExisting:
      enabled: true
  matchConstraints:
    resourceRules:
      - apiGroups: ['']
        apiVersions: ['v1']
        operations: ['CREATE', 'UPDATE']
        resources: ['namespaces']
  variables:
    - name: nsName
      expression: 'object.metadata.name'
    - name: source
      expression: resource.Get("v1", "secrets", "default", "regcred")
  generate:
    - expression: generator.Apply(variables.nsName, [variables.source])
```

기존 네임스페이스가 예를 들어 10개 있는 클러스터에 이 정책을 적용하면, <span class="hl-link" tabindex="0" data-code="generate-secrets-existing.yaml" data-lines="7-8">`generateExisting.enabled: true` 덕분에</span> Kyverno가 그 10개 네임스페이스에 `regcred` 시크릿 복사본을 즉시 만든다. 이 필드가 없으면 정책을 적용한 뒤에 만든 네임스페이스에만 시크릿이 생성된다.

## Kyverno CEL 라이브러리

Kyverno는 쿠버네티스의 CEL 환경에 사용자 정의 함수를 더해 강력한 리소스 생성을 지원한다. 공통 [Kyverno CEL 라이브러리](/docs/policy-types/cel-libraries/)에 더해 `GeneratingPolicy` 유형에는 리소스를 만들고 관리하는 전용 라이브러리가 있다.

### Generator 라이브러리

Kyverno는 리소스 생성을 위한 전용 함수를 제공한다.

| CEL 표현식                                | 용도                                                                                                                                                                                                                                                                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `generator.Apply(namespace, [resources])` | 지정한 네임스페이스에 리소스를 하나 이상 생성한다. 인자는 두 개로, 대상 네임스페이스(문자열)와 적용할 리소스 오브젝트 목록이다. 적용에 성공하면 `true`를 반환하므로 `list.all(...)` 같은 CEL 반복문에서 쓰기 좋다. |

## 예외

정책은 기본적으로 클러스터 전체에 적용된다. 하지만 예외가 필요할 때가 있다. 이럴 때는 [PolicyException](/docs/guides/exceptions#policyexceptions-for-cel-policies)을 사용해 정책을 고치지 않고도 일부 리소스가 정책을 우회하도록 허용할 수 있다. 정책의 보안 수준은 그대로 두고 필요할 때 예외를 줄 수 있다.
